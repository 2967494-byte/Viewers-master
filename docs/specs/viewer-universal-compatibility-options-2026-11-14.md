# Совместимость просмотрщика: варианты резервной отрисовки

Дата: 14 ноября 2026. Исследование вариантов; код и production не изменялись.

## Вывод

Для широкого покрытия нужен путь отображения без обязательного WebGL 2. Облегчение GPU-текстуры помогает при работающем WebGL 2, но не заменяет другой способ отрисовки при отказе создания контекста. Наиболее широкое покрытие слабых устройств даёт серверная реконструкция срезов; локальный CPU/Canvas может быть самостоятельным или промежуточным вариантом.

Нельзя установить причину отказов на компьютерах врачей только по включённой настройке аппаратного ускорения. Нужны результаты проверки конкретного браузера. Невозможно заранее обещать одинаковую скорость и весь функционал на любом устройстве.

## Что подтверждено в текущем проекте

- `platform/app/src/App.tsx`: проверка `checkVolumeRenderingSupport()` выполняется до `appInit`; неудача полностью блокирует приложение, включая функции, которые потенциально могут работать без WebGL.
- `platform/app/src/utils/volumeRenderingSupport.ts`: создаётся WebGL 2 с `powerPreference: high-performance`; проверяются методы, лимит 3D-текстуры и загрузка минимальной R8-текстуры. Ошибка не доказывает физическое отсутствие подходящей видеокарты. Нет подробного отчёта с причинами отказа/сравнением разных параметров создания контекста. Минимальная текстура не подтверждает успешную отрисовку большого медицинского объёма.
- Установлен `@cornerstonejs/core` 4.15.6. `BaseVolumeViewport` явно запрещает CPU fallback для volume viewport. CPU-функции `StackViewport` не заменят три нынешние MPR-плоскости простым флагом.
- `adaptiveVolumeTexture.ts`: уже есть ограничение GPU-памяти и повторные попытки с уменьшением количества отображаемых отсчётов. Это не fallback без WebGL 2.
- `ManualPanorama/RasterView.tsx`: панорама рисуется через Canvas 2D. `reconstruction.ts` содержит выборку значений и построение плоских сечений на CPU. Это задел для отдельного CPU-пути, но загрузка/геометрия/инструменты сейчас связаны с основным движком. Готового независимого MPR из этих компонентов ещё нет.
- Сжатие JPEG2000 примерно 20× уменьшает передачу и хранение. После декодирования размер массива вокселей определяется dimensions и типом данных, а не размером сжатого файла. Существуют также дополнительные CPU/GPU-буферы.

## Опыт других систем и границы применимости

1. **Cornerstone:** документация прежних volume/stack viewport описывает CPU fallback для стека и ошибку для GPU-недоступного объёма — это соответствует установленной версии. Новая документация Generic Viewport отдельно описывает CPU/GPU backends и их переключение с сохранением представления. Это кандидат для прототипа обновления, а не подтверждение, что новый пакет без адаптации сохранит все наши инструменты. Нужна сверка конкретного опубликованного релиза, поддержки CPU volume slices, oblique/slab и интеграции в OHIF.
   - https://v1.cornerstonejs.org/api/core/class/RenderingEngine/
   - https://www.cornerstonejs.org/docs/concepts/cornerstone-core/generic-viewport/render-backends/
2. **DWV:** разработчик описывает MPR, измерения, window/level, pan/zoom в JavaScript/HTML5. Подтверждает существование другой архитектуры браузерного просмотра; не является готовым модулем замены нашего viewer. Совместимость конкретного рендера нужно отдельно проверять, один термин HTML5 этого не доказывает.
   - https://github.com/ivmartel/dwv
3. **MedDream:** официально устанавливает требования к RAM/видеопамяти именно для клиентского MPR/MIP и предупреждает о лимитах памяти браузера. Переход на другой веб-просмотрщик с локальным объёмным рендером сам по себе не гарантирует универсальность.
   - https://meddream.com/documentation/user-guide/client-side-requirements/
4. **Kitware / VTK / trame:** `VtkRemoteView` рендерит на сервере и передаёт клиенту изображения; `VtkRemoteLocalView` сочетает локальный и серверный варианты. В документации есть управление качеством/масштабом кадров для уменьшения задержек взаимодействия. Это готовая основа для исследования серверного пути, но не законченный стоматологический viewer с нашими инструментами.
   - https://github.com/Kitware/trame-vtk#vtkremoteview
   - https://vtk.org/flavors/
5. Атрибуты создания Canvas/WebGL и разные типы контекстов:
   - https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/getContext

## Варианты

### A. Локальные плоскости на CPU + Canvas 2D

Серия скачивается и декодируется на устройстве, нужные сечения рассчитывает CPU, изображение выводится без 3D-текстуры. Вычисления выносятся в Worker; WebAssembly — возможная оптимизация после замеров, а не гарантия отсутствия требований к памяти/графике.

- Цель первого прототипа: три ортогональных среза, общий физический центр, pan/zoom/window-level, простая линейка, готовая панорама.
- Затем: oblique, толщина слоя, фильтры, проекции имплантов, остальные измерения. Не обещать паритет, пока инструменты не адаптированы и не проверены.
- Объёмная 3D-модель не входит в базовый CPU fallback; тяжёлое объёмное программное рендерирование — отдельная задача.
- Плюсы: нет постоянной вычислительной нагрузки на сервер; WebGL 2 не обязателен; можно использовать часть существующей математической основы.
- Ограничения: остаётся скачивание/декодирование серии и расход RAM. На слабом CPU oblique и толстый слой могут обновляться заметно медленнее. Нужны ограничение копий, ленивый кеш срезов, отмена устаревших заданий.
- Первый шаг: сравнить подходящий новый CPU backend Cornerstone с небольшим собственным прототипом на существующем sampler. Не обновлять основной OHIF/Cornerstone без регрессии.

### B. Серверная MPR-реконструкция, браузеру — нужные срезы

Отдельный сервис читает серию из S3, держит ограниченный кеш и строит запрошенные плоскости/панораму. Браузер передаёт координаты и параметры представления, получает результаты и рисует через Canvas 2D. Полный декодированный объём на компьютер врача не загружается.

- Цель: тот же четырёхоконный интерфейс с тремя MPR-плоскостями и панорамой, работающий без WebGL 2 и большого локального массива.
- Оси, положение имплантов и измерения привязаны к физическим координатам исследования. Сервер возвращает геометрию плоскости/шаг/ориентацию/ревизию ответа. Изображение экрана само по себе не источник метрической геометрии.
- Для window/level: либо получать исходные значения плоскости достаточной разрядности и менять окно локально, либо передавать window/level на сервер. Один 8-битный JPEG с зафиксированным окном не заменяет диапазон исходных значений.
- Для частых перемещений: отмена/игнорирование устаревших ответов, объединённый запрос трёх видов, подгрузка соседних срезов, кеш повторных результатов.
- Плюсы: наиболее полезный резерв для слабых компьютеров и телефонов; не требует полноценного GPU у врача; экономит локальную RAM и передачу всего объёма.
- Ограничения: задержка сети, время первого чтения/декодирования сервером, новая нагрузка и эксплуатация render-сервиса. Нужны ограниченный кеш/очереди и тест нескольких одновременных врачей.
- Объёмная 3D-модель может подключаться отдельным серверным рендером позже.

### C. Полный серверный рендер, включая 3D-модель

Сервер рассчитывает и MPR, и объёмную модель; браузер получает готовые изображения/кадры. Для отсутствующего клиентского WebGL нужен именно вывод готовых кадров, а не передача геометрии обратно в WebGL-клиент.

- Плюсы: можно покрыть и тяжёлую 3D-визуализацию на слабом устройстве врача, сохранив оболочку нашего интерфейса.
- Ограничения: самый высокий расход вычислительных ресурсов; интерактивность зависит от сети; серверный CPU/GPU и число одновременных сессий подбираются нагрузочным тестом. API перемещения, инструментов и состояния всё равно нужно интегрировать. Это не бесплатная опция в существующем nginx.
- Совместное использование неизменяемого объёма между сессиями может уменьшить расход памяти; камеры и пользовательские объекты сессий должны оставаться отдельными.

### D. Приложение Windows с собственным рендером

Контролируемая среда и возможность альтернативного CPU/графического backend. Подходит как дополнительный канал для постоянных пользователей и локальной работы.

- Ограничения: установка/обновления; отдельная поддержка платформы; драйверные требования для выбранного 3D backend сохраняются. Одна оболочка Electron с прежним WebGL-viewer не гарантирует решение проблемы.
- Для срочного расширения доступа через браузер это менее прямой путь, чем A/B.

## Что рекомендовано

1. Добавить диагностику и разделить ошибки создания WebGL, форматов, отрисовки и памяти. На проблемных ПК сравнить default/high-performance/low-power с освобождением тестовых контекстов. Собрать версии браузера, фактические лимиты, код ошибки и этап — без DICOM, имён пациентов и launch-токенов. Не отключать проверку без работающего fallback.
2. Для охвата большого числа слабых устройств приоритетно сделать **прототип B: серверные три среза + панорама в нынешней оболочке**. Он решает и отсутствие WebGL, и нехватку клиентской RAM. На работающих компьютерах сохранить локальный быстрый путь.
3. Если важнее обойтись без нового вычислительного сервера, проверить A на одном компьютере врача. Решение принимать по памяти, скорости и объёму переноса инструментов с проверкой на реальном исследовании.
4. Серверную 3D-модель C добавлять, когда подтвердится потребность; базовый fallback ясно обозначает доступные функции. Уменьшенное качество во время движения с возвратом к заданному качеству после остановки допустимо только с явным отображением режима.

## Критерии первого прототипа

- Запуск с принудительно отключённым WebGL и на реальном проблемном ПК; отсутствие вечной загрузки и чёрных окон.
- Одна маленькая и одна большая 16×16 серия, одинаковые контрольные физические координаты в трёх видах.
- Замер первого изображения, обновления при прокрутке, RAM браузера/сервера, ресурсов при 1/5/20 активных пользователях. Цели скорости и лимиты утвердить по результатам, не обещать цифры до замера.
- Сравнение направления осей, интерполяции, spacing, толщины слоя, window/level, линейных размеров и проекций имплантов с нынешним рабочим GPU-путём. Исходные данные и мировая геометрия не меняются ради облегчения.
- Рендер-сервис проверяет существующий доступ к исследованию и актуальное поколение. Кеш ограничен по объёму и сроку и не выдаёт данные другому врачу без ACL. Математические/изображительные данные не отправляются посторонним сервисам.
- Быстрый GPU-путь не переключается и не замедляется без причины; при fallback есть понятная отметка режима и отсутствуют кнопки с неработающими обещаниями.

# Диагностический GPU-профиль 64 МиБ

14 ноября 2026. Предыдущий профиль с одним контекстом не решил сбой Intel HD Graphics 0x0F31. Все 17 изолированных тестов текстур до 16 МиБ на ноутбуке прошли. Следующий эксперимент проверяет предварительное ограничение scalar texture снимка до 64 МиБ; общая память приложения этим не ограничена. Причина потери контекста пока не доказана.

## Включение и выключение

На `https://admin.orbital3d.ru/3dviewer/gpu-check.html` добавлена отдельная секция с кнопками включения/выключения и скачивания журнала. Флаг `orbital:gpu-diagnostic-profile:v1 = 64` сохраняется только в localStorage данного origin/браузера. Он считывается до `cs3DInit`; включение и выключение требуют закрыть прежний viewer и открыть исследование заново из карточки. Обычный режим и имеющаяся настройка `compatibility` не меняются. Никакого автоматического включения для других пользователей нет.

В тестовом профиле в верхней панели видна отметка «64 МиБ»; на MPR сохраняется существующая подпись уменьшенного шага отображения. Объёмные размеры, физическая геометрия и исходные воксели не меняются, уменьшается количество Z-слоёв в GPU-текстуре. Детализация снижается, поэтому это диагностический эксперимент, не подтверждение пригодности полученного изображения для клинических решений. CPU-эксперимент остаётся отключённым и вне сборки.

## Журнал

`orbital:gpu-render-report:v1`: начало сессии, начало/окончание core init, конфигурация объёма, размеры/формат/байты перед выделением, результат выделения, прогресс уникальных загруженных позиций, завершение загрузки и потеря контекста. Запись перед опасной операцией позволяет сохранить последний известный этап даже при падении GPU-процесса. Сохранение localStorage не гарантируется при полном аварийном завершении браузера; ошибки хранилища не прерывают просмотрщик.

Максимум 80 событий, примерно 16 промежуточных записей на загрузку текстуры. Повторные записи одного слоя не считаются завершением объёма. Без тестового флага журнал не создаётся и прежний отчёт не стирается. Встроенные события не содержат ФИО, UID, URL, ключей S3 или токенов. Автоматической отправки по сети нет; экспорт — по кнопке пользователя. Последний отчёт заменяется следующим запуском viewer с включённым профилем, время сессии присутствует в `startedAt`.

## Расширенная проверка на Intel прошла

Файл пользователя `D:/orbital-gpu-check-2026-11-14T15-59-26-913Z.txt`: v2, streamed-400x400-16-64MiB, completed, 13/13 OK. В том числе R16_SNORM 400×400×209 и R32F до 64 МиБ с загрузкой и отрисовкой. Это подтверждает работу этих изолированных операций на ноутбуке, но не исключает общую нехватку ресурсов или сбой конкретного шейдера/операции полного движка.

Из исходников установленного Cornerstone: общий offscreen buffer использует максимум ширины/высоты viewport, не сумму экранов; scalar texture передаётся shared mapper. Явного завышения размера из этих алгоритмов не установлено. MPR использует полноценный volume mapper со своими transfer-function текстурами, шейдерами и буферами. Причина сбоя пока не доказана.

Добавлен `gpuEngineDiagnostics.ts`, включаемый только при существующем opt-in профиле 64 МиБ. На реальном GL-контексте наблюдает первые texImage2D/texStorage2D/renderbufferStorage/bufferData, shaderSource (только длину, не код), compileShader/linkProgram и draw-вызовы. На engine наблюдает первые четыре рендера каждого viewport: размер canvas, slabThickness, sampleDistance, maximumSamplesPerRay и размеры LUT. Вызовы делегируются с исходным receiver/аргументами/результатом; исключения пробрасываются. Наблюдатель не вызывает getError, не добавляет finish и не меняет параметры или порядок рендера. В обычном режиме native API не оборачивается.

Журнал ограничен 160 событиями; частота native draw-записей ограничена первыми 12 вызовами каждого типа. Это диагностическая синхронная запись и может влиять на время работы JS, но не является измерением длительности исполнения команд GPU: elapsedMs показывает длительность вызова на стороне JS. Export использует прежнюю кнопку «Скачать журнал просмотрщика».

Регрессия: 53 набора, 375 passed, 1 skipped. Четыре дополнительных сценария проверяют выключенный режим, native receiver/аргументы/результат и сохранение GL error state, исключения/предел draw-записей, параметры viewport/mapper. Production webpack успешно с тремя прежними предупреждениями.

### Найден скрытый объёмный рендер

Предварительная сборка с наблюдателем локально показала `viewport-render-start type=volume3d`, clippingPlanes=0, sampleDistance≈0,1, canvas≈800×415 при видимой автопанораме. Автопанорама — DOM-сосед viewport canvas; существующий ContextPool продолжает рендерить накрытый 3D-череп при обновлениях объёма. Это подтверждённая лишняя работа, но причинная связь со сбоем Intel требует теста на ноутбуке.

До публикации добавлен `hiddenPanoramaRenderGuard.ts`: пропускает вызов движка только для `mpr-3d`, если в его собственном `.viewport-wrapper` непосредственно присутствует `.automatic-panorama-pane`. Другие viewport/layout не затрагиваются. Камера/акторы/геометрия/текстуры не удаляются. Пропуск не порождает IMAGE_RENDERED. При переключении на череп React сначала удаляет покрытие, затем эффект явно запрашивает `viewport.render()`. При возврате на панораму фоновые ray-cast вызовы снова пропускаются. Guard включён для скрытого окна независимо от диагностического флага; расширенное наблюдение native GL остаётся opt-in.

Первый пакет выше не публиковался; итоговая сборка включает guard и подлежит повторной проверке рендера/переключения черепа и автопанорамы.

Итоговая регрессия: 54 набора, 378 passed, 1 skipped. Три guard-теста проверяют отсутствие GPU-вызова/ложного IMAGE_RENDERED для накрытого черепа, возобновление того же renderer после снятия покрытия и повторное подавление при возврате, отсутствие влияния на остальные viewport/layout и сохранение аргументов/receiver.

## 1. Обязательный результат

1. Пользователь загружает готовый архив существующим обычным способом. Специальная локальная упаковка/RLE-подготовка через Orbital Uploader не нужна.
2. Существующий процесс распаковывает архив в HOT и проверяет исходные DICOM.
3. Отдельная фоновая служба автоматически формирует сжатую копию JPEG 2000, стартовый профиль **20×**, рядом с исходными файлами в HOT.
4. Служба проверяет результат и публикует индекс/manifest готовой серии.
5. Наш viewer доступен только при одновременном наличии права пользователя, доступа к конкретному исследованию и готовой актуальной сжатой серии.
6. Только суперадминистратор получает право использования viewer автоматически. Для всех остальных ролей право выдаётся индивидуально через админку.
7. Viewer получает срезы напрямую из S3 по временным подписанным URL. Flask не проксирует пиксели и не перекодирует их при открытии.

Исходный архив и исходные распакованные DICOM сохраняются. Старые способы скачивания/внешнего просмотра продолжают работать.

- Централизовать проверки и использовать их в шаблонах, status API, создании launch token, resolver, старых HTTP metadata/online endpoints. Скрытая кнопка не является защитой API.
- Сохранить действующие ограничения управления правами: обычный админ не повышает собственные права и не меняет права суперадмина. Другие ключи `permissions` при сохранении не теряются.
- Не менять глобально семантику `User.has_permission` ради этого viewer; использовать отдельный helper с явным исключением `superadmin`.
- Аудировать выдачу/отзыв права. При отзыве запрещать новые открытия и повторное разрешение токенов.

## 5. Готовность исследования и интерфейс

Разделить `hot_status` исходника и статус подготовки viewer. `hot_status=ready` и `hot_has_dicom=true` сами по себе новый viewer не включают.

```text
viewer_available = can_use_online_viewer
    and can_access_this_study
    and source_hot_ready
    and compressed_representation_ready
    and current_source_version_matches
    and not_expired
```

Суперадминистратор также не открывает отсутствующую, неполную или просроченную сжатую серию.

UI в журнале, карточках пациента/приёма и кабинетах врача/клиники:

- Нет права — не показывать действие нового viewer.
- Право есть, задача в очереди — неактивное действие «Ожидает подготовки».
- Идёт обработка — «Подготовка просмотра — N%».
- Ready — кнопка «Открыть ORBITAL 3D» в новой вкладке.
- Failed — «Не удалось подготовить просмотр»; повтор подготовки доступен уполномоченному сотруднику, не каждому врачу.
- Expired/удалено/неподдерживаемый тип — соответствующее понятное состояние, без попытки открытия оригиналов.

Статус получать пакетно из БД, без HEAD каждого среза и без обхода S3 на каждую строку журнала. При фактическом запуске повторно проверять актуальность опубликованного указателя/manifest; повреждение/404 снимает готовность и обрабатывается задачей восстановления.
Новый viewer не запускает VM/Ez3D/Guacamole и не занимает их рабочие станции или квоты. Существующие отдельные кнопки внешних просмотрщиков сохраняются.

## 6. Служба сжатия и данные задач

Выделить отдельный процесс worker, запускаемый службой, с устойчивыми jobs в БД либо существующей надёжной очереди. Не использовать daemon-thread Flask, память Gunicorn или длительный HTTP-запрос как единственное место выполнения.
Оформить как `viewer_compression_worker.py` и отдельный unit systemd по принятой в CRM структуре. Начальное размещение — сервер CRM, с общей PostgreSQL и действующей S3-конфигурацией, отдельным процессом от web/panorama. Ограничить ресурсы и начать с одного задания одновременно; возможность вынести worker на отдельную машину сохранить. На VPS статического viewer `95.163.231.17` службу сжатия по умолчанию не размещать. Фактический запас ресурсов CRM проверить до включения; при нехватке вынести worker, не увеличивать параллелизм вслепую.

Предусмотреть данные job/representation:

- ID и тип исходного объекта, study/source version, ключ/версия/хеш архива, HOT root.
- Profile ID/version, generation ID, fingerprint, путь опубликованного manifest.
- Статусы `queued → running → validating → publishing → ready`; отдельно `failed`, `superseded`, `expired`, причина unsupported.
- Стадия, число обработанных/всех файлов и кадров, процент, heartbeat/lease, attempts, ошибка, timestamps, общий `expiresAt`.
- Исходные/выходные байты, размер индекса, фактические коэффициенты и длительность.

Постановку задачи связать транзакционно с завершением распаковки либо использовать outbox. Добавить reconciliation: пропущенное событие для готового HOT без активной/готовой задачи восстанавливается.
Ключ идемпотентности: конкретное исследование + source version/fingerprint + profile version. Изменение исходного архива немедленно инвалидирует готовность старого результата и токены его запуска.
Worker использует lease/heartbeat; перед публикацией проверяет актуальность источника, свои полномочия lease и срок. Старое задание не публикует результат после замены или удаления исследования.
Ограничить повторы, параллелизм, CPU/RAM/диск и размер spool. Начать с одной серии одновременно. Подготовка viewer не меняет готовность исходника и не дублирует существующие уведомления «исследование готово».
Опционально использовать проверенные локальные файлы, оставшиеся после распаковки, чтобы не скачивать их снова. Путь из уже удаляемого TemporaryDirectory передавать нельзя; при утрате spool восстанавливаться из HOT.

## 7. Кодек и профиль 20×

- JPEG 2000 irreversible внутри стандартного DICOM, TransferSyntaxUID **`1.2.840.10008.1.2.4.91`**.
- Начальный стек: pydicom + pylibjpeg + pylibjpeg-openjpeg; зависимости зафиксировать и изолировать от существующих служб.
- Сохранить все срезы, Rows/Columns, геометрию, 16-битный диапазон и signedness, slope/intercept, фотометрию и функциональные группы там, где они поддержаны.
- Не уменьшать картинки до JPEG/PNG 8-bit, не применять постоянное окно яркости, не пропускать каждый второй срез и не уменьшать пространственную сетку в первом профиле.
- Назначить новые Series/SOP UID производным, согласовать file meta, записать DERIVED, признаки/метод/коэффициент потерь и ссылки на исходные инстансы. Сохранять историю ранее имевшихся потерь.
- Каждую новую версию получать из исходной серии, не из предыдущей сжатой копии.
- Повторно декодировать каждый выходной файл, проверить число кадров, UID, геометрию, диапазоны и измеренные ошибки. Битый/неполный набор не публиковать.
- Формат считать по содержимому, а не только по расширению: DICOM может иметь другое имя. Явно поддержать/отклонить необычные syntaxes, multiframe, локализаторы и не-DICOM; отказ по одной серии не скрывать.

Основная КТ и scout: публиковать полностью проверенные поддерживаемые объёмные серии; отдельно распознанные 2D-localizer/scout/preview не включать в 3D-manifest, сохраняя их оригиналы и причину исключения в метаданных задачи. Их наличие не блокирует готовую основную КТ. Классифицировать по DICOM-типу объекта, ImageType/FrameType (включая LOCALIZER), числу кадров и геометрии, не по одному имени файла, SeriesDescription или количеству файлов. Один Enhanced/multiframe DICOM может содержать полноценный объём. При смешанном/неясном составе не отбрасывать срезы молча; ошибка декодирования, пропуск или ошибка кодирования внутри выбранного объёма блокирует публикацию этого результата. Если поддерживаемых объёмов нет — unsupported, без активной кнопки. Проверка должна различать объёмный multiframe, один 2D-scout и повреждённый основной объём. Основание: [DICOM CT Image Type](https://dicom.nema.org/medical/Dicom/2024c/output/chtml/part03/sect_C.8.2.html) и [Enhanced CT](https://dicom.nema.org/medical/dicom/2023d/output/chtml/part03/sect_C.8.15.2.html).

20× — настраиваемый стартовый профиль, а не обещание одного размера/качества для любого аппарата.
В локальном пилоте: 450 срезов 600×600, signed 16-bit, 0,2 мм; DICOM 324 732 268 → 16 220 740 байт (20,02×), индекс дополнительно 1 760 327 байт. Пользователь подтвердил открытие в viewer.
В том опыте `j2k_cr=21.083107697446525` компенсировал заголовки для результата около 20× по файлам. Не копировать эту поправку как универсальную для всех исследований.
Различать raw-pixel ratio, уменьшение текущих DICOM и итог с индексом. Не повышать агрессивность автоматически ради 20× относительно входа, уже сжатого без потерь/с потерями. Для слишком большого результата фиксировать фактический коэффициент и сохранять принятую политику качества.
Для дальнейшего подбора разрешить менять настройки профиля администратору; новую конфигурацию версионировать. Перекодирование по каждому открытию или движению пользовательского ползунка запрещено.

## 8. Точное расположение и JSON-контракт v1

```text
hot/.../appt_<id>/
  <существующие исходные файлы>
  _viewer/
    representations.json
    <sourceVersion>/jpeg2000-20x/<generationId>/
      manifest.json
      <seriesId>/
        ohif_metadata.json
        instances/000001.dcm
```

`_viewer/representations.json`, пути относительно `_viewer/`:

```json
{
  "schemaVersion": 1,
  "sourceVersion": 1,
  "expiresAt": "2026-12-04T12:00:00Z",
  "defaultRepresentationId": "jpeg2000-20x",
  "representations": [
    { "id": "jpeg2000-20x", "status": "ready", "manifest": "1/jpeg2000-20x/generation-001/manifest.json" }
  ]
}
```

Manifest, пути индексов относительно каталога manifest:

```json
{
  "schemaVersion": 1,
  "id": "jpeg2000-20x",
  "status": "ready",
  "sourceVersion": 1,
  "expiresAt": "2026-12-04T12:00:00Z",
  "profile": { "codec": "jpeg2000", "targetRatio": 20 },
  "series": [
    { "id": "derived-series-1", "index": "derived-series-1/ohif_metadata.json", "instanceCount": 450 }
  ]
}
```

Примерные даты заменяются реальными UTC timestamp; sourceVersion берётся из текущей версии источника.
`instanceCount` — число DICOM-инстансов/файлов, не количество всех кадров multiframe.
Индексы генерируются из окончательных производных DICOM: массив DICOM JSON (HEX с vr/Value либо натурализованные поля) с `_url: "instances/000001.dcm"`, относительным к индексу.
Все обязательные UID, IPP/IOP, PixelSpacing, Rows/Columns, pixel representation и window/rescale metadata должны быть корректны.
URL и пути исходников в таком индексе недопустимы; viewer принимает только относительные пути внутри опубликованного поколения. Имена выходных файлов заканчиваются `.dcm`.

Публикация: уникальный generation-prefix → все DICOM → проверенные индексы → ready-manifest → **последним PUT representations.json**. После подтверждения публикации фиксируется ready в БД.
Обрабатывать восстановление после сбоев между S3 PUT и DB commit; указатель и БД должны быть сверяемыми. Не перезаписывать активный набор пофайлово.

## 9. Запуск и resolver CRM

Реализовать серверное создание короткоживущего непредсказуемого launch token, привязанного к текущему пользователю/сессии, конкретному исследованию и source version. Например, POST launch endpoint с CSRF; точный новый launch URL выбрать по структуре CRM.
После проверок возвращать URL `<VIEWER_PUBLIC_BASE_URL>/v/<token>`, где base содержит `/3dviewer/`.
Нужен **точный endpoint `GET /api/viewer/resolve/<token>` на корне CRM**, поскольку он уже ожидается выложенным viewer. У существующего blueprint `viewer` префикс `/viewer`: не получить случайно `/viewer/api/viewer/resolve/...`.

Resolver получает `credentials: include`, проверяет login/session, состояние аккаунта, право viewer, доступ к этому снимку, source version, актуальность manifest и срок. Повторная проверка нужна даже для ранее выданного токена.
В ответе не использовать redirect на HTML login; JSON 401/403/404/409/410 по ситуации. Ошибки не раскрывают содержимое чужого исследования.

Успешный формат:

```json
{
  "schemaVersion": 1,
  "viewerAvailable": true,
  "s3Prefix": "hot/2026/11/04/pat_1/appt_2/",
  "sourceVersion": 1,
  "access": {
    "expiresAt": "2026-11-04T13:20:00Z",
    "resources": {
      "hot/2026/11/04/pat_1/appt_2/_viewer/representations.json": "<полный подписанный S3 GET URL>",
      "<точный object key manifest>": "<подписанный GET URL>",
      "<точный object key каждого индекса>": "<подписанный GET URL>",
      "<точный object key каждого DICOM>": "<подписанный GET URL>"
    }
  }
}
```

- `resources` должен содержать указатель, выбранный manifest, все индексы и все файлы серий, перечисленных в нём. Wildcards не поддерживаются.
- Подписывать только ключи внутри `_viewer/` этого исследования, из проверенного опубликованного поколения. Не подписывать полученный от клиента произвольный prefix/key.
- Signed URL — path-style `https://<endpoint>/<bucket>/<object key>?...`, с корректным percent-encoding. Установленный viewer сверяет endpoint origin, bucket и точный key.
- TTL launch token и TTL signed URLs — разные настройки. Предлагаемые стартовые значения: 2 минуты для начала открытия и 15 минут для access; access не дольше общего expiresAt. Signed URL действителен не меньше объявленного access.expiresAt.
- Постоянные ключи S3 браузеру не передавать. Не проксировать сами DICOM через Flask.
- Токены, query подписи и JSON с signed URLs не писать в логи/аналитику. Resolver выдаёт no-store; для token routes настроить безопасное логирование и no-referrer.
- Старую кнопку «Онлайн 3D» заменить действием «Открыть ORBITAL 3D» с новыми правами и состояниями готовности. После переключения интерфейса устаревший HTTP-протокол `/viewer/online/<id>` и `/viewer/metadata/<id>` закрыть: после проверки авторизации/доступа возвращать понятный 410 (для metadata — JSON), без исходных ссылок и без запуска прежнего viewer. Extra-варианты также не оставлять обходом; несовместимые extras нового viewer не получают. Отдельные RDP/Ez3D-сервисы не ломать. Закрытие старых HTTP routes и переключение UI включать согласованно одним feature flag/релизом, чтобы не оставить действующую кнопку на закрытом endpoint.

## 10. Раздельные исследования и дополнительные файлы

Нельзя смешивать основной DicomStudy, разные серии и AppointmentExtraStudy только потому, что у них один appointment_id.
Для каждого источника собственные version/fingerprint, job и привязка готовности. JPG/PNG/PDF и нераспакованный `zip_raw` не становятся 3D-исследованием автоматически.

Выявленная зависимость: текущий viewer v1 вычисляет корень по сегменту `appt_...`. Основные исследования соответствуют этому пути, а существующие extras могут лежать в `hot/<appointment_id>/<uuid>.../`, без такого сегмента. Вложенный extra под первым `appt_...` также может быть усечён до основного корня.
Поэтому нельзя включать viewer для extras или выдавать им pointer основной серии без проверки совместимости.

Основная приёмка этой версии — DicomStudy. В реализации сервиса предусмотреть тип источника для extras, изучить фактические пути и отдельно описать нужное расширение контракта viewer для их открытия. Если оно требуется, оставить новый viewer для таких extras недоступным с понятной причиной до согласованной правки viewer. Существующая выдача extras сохраняется. Не переносить исходники и не придумывать обходной S3-root, чтобы молча обойти это ограничение.

## 11. Срок хранения, замена и удаление

- Производные размещаются в том же HOT-префиксе и подчиняются его политике хранения.
- Зафиксировать общий срок от HOT-сессии, стартово 30 дней. Перекодирование не продлевает его.
- На общем expiresAt отключать выдачу и удалять набор по принятой политике. S3 lifecycle по возрасту отдельного объекта может удалить более позднюю копию позже исходника; это не синхронное удаление всей папки.
- Проверить реальные lifecycle/versioning rules; для строгого общего срока нужен плановый cleanup, а не только поле в JSON. Не менять все правила бакета вслепую и не трогать долгосрочный archive/.
- При удалении отменять jobs, инвалидировать токены/указатели и не позволять worker восстановить удалённое.
- Повторное восстановление из архива — явная новая HOT-сессия с корректным сроком и source identity.
- Старые распакованные исследования можно подготовить ограниченным batch без повторной загрузки. Массовый backfill при первой выкладке автоматически не запускать.

## 12. Совместимость с существующими службами

Рекурсивные читатели исходного HOT должны исключать `_viewer/`: генератор исходного metadata JSON, серверная панорама, настольная выдача, скачивание/ZIP-сборка, подсчёт исходных файлов и проверка наличия DICOM.
Особенно проверить `StorageManager.download_hot_to_temp`: сейчас он скачивает всё под prefix и использует basename, что создаёт смешивание/коллизии производных и исходников.
Для источника и производной версии использовать точные индексы/списки и сохранять структуру каталогов.
Полное удаление исследования, наоборот, должно охватывать `_viewer/`.

## 13. Конфигурация и инфраструктурные зависимости

Предусмотреть в конфигурации: включение новой функции, адрес viewer, allowed viewer origins, compressor profile/version/параметры, worker limits, TTL, storage lifetime и настройки S3 из действующего storage config. Секреты только через существующий механизм окружения.
Целевая production-схема: отдельный viewer origin `https://viewer.orbital3d.ru` на существующем VPS, `VIEWER_PUBLIC_BASE_URL=https://viewer.orbital3d.ru/3dviewer/`, запуск `https://viewer.orbital3d.ru/3dviewer/v/<token>`. CRM остаётся на `https://admin.orbital3d.ru`, resolver — `https://admin.orbital3d.ru/api/viewer/resolve/<token>`. Не проксировать всю статику через CRM в стартовой реализации. URL и origin настраиваются окружением, не зашиваются в контроллеры.
Это целевое решение, не утверждение о действующей DNS/HTTPS-конфигурации: сейчас Nginx VPS слушает только loopback. Домен, сертификат и публичный вход ещё нужно настроить отдельным инфраструктурным шагом с сохранением COOP/COEP. Не хардкодить адресом врачам `127.0.0.1:18080`: это локальный SSH-туннель разработчика; IP с обычным HTTP не заменяет production HTTPS.
Оба HTTPS-поддомена имеют разные origins, но один schemeful site. Для этой схемы достаточно явного `SESSION_COOKIE_SAMESITE=Lax`; не переводить CRM глобально на `None`. Production-cookie: Secure, HttpOnly, Path=/; предпочтительно host-only для admin.orbital3d.ru, без расширения Domain на весь orbital3d.ru. Viewer не получает cookie CRM: браузер посылает её на адрес CRM в resolver fetch с `credentials: include`. См. [MDN Site](https://developer.mozilla.org/en-US/docs/Glossary/Site) и [Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie).
В resolver CORS разрешить ровно `https://viewer.orbital3d.ru`, `Access-Control-Allow-Credentials: true`, `Vary: Origin`, включая ответы ошибок; не wildcard. Не включать credentials-CORS глобально для всех endpoint. Проверить реальный браузерный сценарий и настройки Path/Domain действующей cookie. См. [MDN CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS).
Локальные интеграционные тесты: отдельные dev URL/origins и конфигурация S3; оба приложения на одном имени хоста и одной схеме (например, localhost с разными портами) либо на HTTPS dev-поддоменах. Сценарий локальный viewer → production CRM cross-site не считать основанием ослаблять боевые cookie. Не отключать браузерную защиту для прохождения тестов.
В S3 разрешить необходимые GET/CORS/headers для viewer. Не открывать bucket публично.
Источник истины для production S3 — эффективная конфигурация действующей CRM (`S3_ENDPOINT_URL`, `S3_BUCKET_NAME`, region и другие параметры клиента), загруженная обычным механизмом приложения. Worker использует тот же storage config. Не выбирать storage по defaults из исходников. В коде CRM defaults Reg.ru, а текущий viewer настроен на Yandex `orbital3d-hot-storage`; реальные настройки могут отличаться. При расхождении не менять bucket CRM и не переносить архивы наугад: подготовить параметры endpoint/bucket/region для синхронизации runtime app-config.js viewer отдельным шагом выкладки. Секреты S3 в этот JS не переносить. До синхронизации реальную интеграцию не считать принятой. Локальное сжатие/тест публикации — отдельный тестовый бакет либо изолированный prefix и ограниченные права без перезаписи боевых исследований.

## 15. Проверки и критерии приёмки

1. Обычная загрузка готового архива работает без Uploader; распаковка и прежняя выдача не сломаны.
2. Все не-superadmin роли без флажка получают отказ и через прямой URL/API. Суперадмин имеет право автоматически, но ждёт готовой серии.
3. Пользователь с флажком не открывает чужое исследование; свой/разрешённый shared access работает. Подмена study/token/sourceVersion отклоняется.
4. Полный процесс upload → HOT ready → worker → validated publication → active button → реальный viewer работает.
5. 20×-серия корректно декодируется в browser; число кадров/геометрия сохранены, исходники не изменены. Есть реальный отчёт размеров/ошибок/времени, а не только synthetic test.
6. Неполные, failed, stale, expired и отсутствующие результаты не дают active button/подписанных исходников; нет чтения оригиналов как fallback.
7. Дублированное событие и рестарт worker не создают несколько активных jobs. Смена/удаление источника во время encode/upload не публикует старый результат.
8. Ошибка compressor не сбивает `hot_status` и не ломает исходный архив; попытки и ошибки видны сотруднику.
9. Resolver отдаёт точный schemaVersion 1 payload; все URL находятся в разрешённом поколении, действуют в пределах срока, без постоянных S3 credentials. Закрыты старые обходные metadata endpoints.
10. Обе стороны CORS/HTTPS/COOP/COEP работают на настоящем адресе viewer. Туннель считается тестовым доступом.
11. Панорама, скачивание, extras, VM/Ez3D и lifecycle проверены на отсутствие смешивания; для несовместимого extra-root явно указан статус и следующая зависимость.
12. Истечение срока/отзыв права запрещают новые выдачи; поведение уже выданных URL соответствует TTL, а не обещанию мгновенного отзыва.
13. Архив с основной КТ и отдельным scout даёт готовый основной объём и записанную причину исключения scout; один поддерживаемый multiframe-объём не ошибочно исключается по числу файлов. Повреждённый основной объём не превращается в ready путём молчаливого удаления неудачных срезов.

## 16. Порядок работы и результат от Gemini

Сначала изучить код/инструкции проекта и контракт viewer, затем реализовать изменения по этапам: permissions и модели → encoder/worker → публикация HOT → status/launch/resolver → UI → регрессии и реальная интеграция.
Сделать миграции и команды/службу запуска, настройку профиля 20×, ограниченный backfill и инструкции по очистке/повтору. Не ставить тяжёлое сжатие в web-request.

Перед выкладкой: backup БД, проверка миграций, отдельно включаемый worker с одним активным исследованием, тестовая группа, проверка суперадмином, затем индивидуальная выдача прав. Архивы и другие permission keys не теряются. Массовой конвертации и автоматического включения права всем нет.
Rollback отключает новую выдачу/постановку задач и останавливает worker; существующие загрузка/скачивание/внешний просмотр продолжают работать. Миграции/откат не удаляют исходные исследования.

В завершении предоставить: список изменений, применённую схему БД, конфигурацию без секретов, команды запуска, отчёт тестов и реального полного цикла, результаты сжатия, инструкцию выкладки/отката и список оставшихся внешних зависимостей (домен/CORS/S3/extra-root). Не заявлять готовность production только по unit-тестам или наличию папки в S3.

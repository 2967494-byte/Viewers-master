# Задание для Cursor. Этап 1: автономное развёртывание Orbital3D Viewer на VPS

Обновлено: 27 октября 2026 года.

Эта редакция заменяет прежнее задание на сквозную интеграцию. **Выполняется только первый этап.** Подключение хранилища, основного сервера и кабинета, настройка домена в это задание не входят. Их подробные задания пока не составляются.

Документ описывает предстоящую работу. Сам факт его подготовки не означает, что сборка или развёртывание выполнены. Команды и конфигурации нужно сверить с фактическими исходниками и целевым VPS.

## 1. Разделение проекта на этапы

1. **Сейчас: автономный просмотрщик на VPS**, локальное открытие DICOM на компьютере пользователя, проверка интерфейса и инструментов.
2. Позже: подключение S3 и самостоятельные тесты вне CRM. Подробности пока не разрабатывать.
3. Позже: доменное имя и интеграция с CRM. Подробности пока не разрабатывать.

По завершении первого этапа остановиться и передать результат. Не начинать следующие этапы самостоятельно.

## 2. Цель первого этапа

Развернуть production-сборку текущего форка Orbital3D Viewer на отдельном VPS:

- 2 vCPU;
- 4 ГБ RAM;
- 30 ГБ SSD/NVMe;
- Ubuntu Server 24.04 LTS, x86-64;
- доступ по SSH;
- без зависимости от других серверов проекта.

Пользователь получает приложение с VPS и выбирает **локальные DICOM-файлы или папку на своём компьютере**. Браузер открывает исследование, строит MPR, 3D и автопанораму, позволяет использовать существующие стоматологические инструменты.

DICOM не отправляются на VPS. Сервер раздаёт JS, CSS, WASM, worker-файлы, шрифты и другие ресурсы приложения. Никакой серверный расчёт панорамы не запускается.

### Что входит

- проверка исходников и сохранение актуальных кастомизаций;
- отдельная автономная конфигурация сборки;
- рабочая стартовая страница локального открытия исследования;
- production-сборка на рабочей машине/CI;
- установка Nginx на VPS;
- доступ для тестирования без домена через SSH-туннель;
- необходимые browser headers для workers/SharedArrayBuffer;
- перенос релиза, проверка файлов и переключение версии;
- проверка инструментов на тестовых локальных DICOM;
- проверка повторного обновления и отката.

### Что в этот этап не входит

- изменения `patient_accounting_system`, Flask, БД и CRM;
- доступ к кабинету врача/лаборанта, cookies, CORS API и кнопкам основного сайта;
- подключение S3, выдача подписанных ссылок, изменение bucket/CORS/ключей;
- изменение загрузки ZIP, Orbital Uploader и подготовки `hot/`;
- серверная распаковка, сжатие или обработка DICOM;
- DNS, доменное имя, публичный HTTPS и ACME/Certbot;
- перенос существующих сервисов, развёртывание `panorama-server/`;
- оптимизация серверных TCP-буферов или BBR;
- обещание проверки скорости получения исследований из хранилища;
- публичный запуск для всех врачей.

## 3. Как тестировать без домена

Открывать обычный `http://<публичный-IP>/` для полноценной приёмки недостаточно: внешнее HTTP-окружение не считается secure context. Это может ограничить SharedArrayBuffer и связанные возможности просмотрщика.

Основной способ этого этапа:

```text
Браузер на компьютере пользователя
  http://localhost:18080/3dviewer/
       |
       | локальное перенаправление SSH, зашифрованное соединение до VPS
       v
VPS: Nginx слушает только 127.0.0.1:8080
       |
       +-- раздаёт production-ресурсы просмотрщика

Локальные DICOM пользователя --> память браузера --> MPR / 3D / панорама
```

`localhost` в современных поддерживаемых браузерах относится к потенциально доверенным origins даже при HTTP. С COOP/COEP это позволяет проверить необходимые функции, не занимаясь пока DNS и публичным сертификатом.

При этом приложение действительно приходит с VPS, а не запускается локальным dev-server. SSH-туннель не передаёт DICOM на VPS: через него браузер получает только ресурсы приложения.

Доступ осуществляется с компьютера, где запущен туннель. На втором компьютере нужно собственное разрешённое SSH-подключение и свой туннель. Это временный тестовый способ, не схема массового доступа врачей.

Не использовать браузерные флаги обхода secure context, `--disable-web-security` или отключение нужных функций, чтобы скрыть проблему запуска.

## 7. Автономная конфигурация и стартовая страница

Создать отдельный файл, например:

```text
platform/app/public/config/standalone.js
```

Имя предлагается этим заданием; готовой настройки с таким именем пока нет. За основу брать конфигурацию действующего форка, а не пример стороннего PACS.

Обязательное поведение:

1. `routerBasename: '/3dviewer/'`.
2. Рабочий `dicomlocal` datasource и режим `segmentation/dicomlocal`.
3. Открытие `/3dviewer/` показывает страницу с выбором локальных файлов/папки.
4. После выбора DICOM открывается существующий стоматологический режим MPR.
5. Нет автоматических запросов к CRM, S3, удалённым PACS или token API.
6. Кнопка облачного хранилища и сетевые способы открытия на этом этапе не предлагаются пользователю.
7. Текущая локальная обработка и инструменты сохраняются.

Важная особенность форка: корневой маршрут локального открытия сейчас добавляется при `showStudyList: true`. Несмотря на название, отключение этого флага может убрать нужную стартовую страницу. Сохранить его либо явно реализовать и проверить автономный root route. Не менять значение вслепую.

Маршрут `/local` в текущем коде получает другой `modePath`; не считать его автоматически эквивалентным корневой странице. Проверять конечный переход именно в `segmentation/dicomlocal`.

Кнопку «Облачное хранилище S3» скрыть/отключить через понятный флаг автономной конфигурации с проверкой фактического использования в UI. Не ограничиваться неиспользуемым полем config. На этом этапе не переписывать механизм S3 и не реализовывать его подключение.

В автономной сборке также не должен работать `/v/:token`, который сейчас обращается к API и имеет Base64 fallback. Сетевые входы нужно выключить для этого профиля; сохранить код будущих сценариев отдельно, если он нужен разработке.

Локальное открытие означает реальные DICOM-файлы/папку, а не загрузку архива на сервер. Не обещать поддержку ZIP, если её нет в текущем локальном обработчике.

### Секреты и сетевые обращения

В конфигурациях сборки есть возможность подстановки S3 access key/secret key в JavaScript. Автономному профилю они не нужны и не должны попадать в артефакт.

- Собирать в чистом окружении без `.env` серверов проекта и без S3-секретов.
- Проверить Webpack DefinePlugin, Dotenv и другие реальные пути подстановки.
- Не передавать реальные credentials, чтобы «просто заработала сборка».
- Проверить итоговые JS/config/архив на отсутствие секретных значений, не печатая их.
- `preinstall.js` может вывести команду с `GITHUB_TOKEN`; не передавать туда токен без устранения такого логирования.
- Наличие строк с названиями env-переменных само по себе не означает утечку: проверяются реальные значения и доступные способы обращения.
- В Network при локальном открытии не должно быть запросов к `admin.orbital3d.ru`, S3 или другим серверам данных. Допустимы ресурсы самого приложения и локальные `blob:` URL.

Это проверка самостоятельности первого этапа. Доступ к действующим ключам и настройкам хранилища не требуется.

## 8. Сборка вне VPS

Собирать на рабочей машине или CI. Ориентир для build-машины — 16 ГБ RAM: в текущем script Webpack разрешён heap около 8 ГБ. На VPS с 4 ГБ production-сборку не выполнять.

Использовать поддерживаемую совместимую Node.js LTS; начать проверку с Node.js 22 LTS и Yarn 1.22.22. Записать точные версии, на которых сборка успешно прошла. Не обновлять зависимости и lockfile ради этого этапа без выявленной необходимости.

Из корня чистого снимка:

```bash
node --version
yarn --version
yarn install --frozen-lockfile
```

Не использовать `install:dev` с другим addOns lockfile, `install:update-lockfile` или dev-server для production. Проверить требуемые сборкой `version.txt`, `commit.txt` и генерируемые импорты расширений.

### Стабильный маршрут и ресурсы релиза

Сразу разделить:

```text
Маршрут приложения: /3dviewer/
Ресурсы релиза:     /releases/<RELEASE_ID>/3dviewer/
Router basename:   /3dviewer/
```

Так открытая старая вкладка продолжает получать свои JS chunks, workers и WASM после публикации новой версии. В этом форке `PUBLIC_URL` отвечает за ресурсы, а `routerBasename` читается из config. Подтвердить их независимую работу реальной сборкой и браузером.

Пример Bash на build-машине:

```bash
RELEASE_ID="$(date -u +%Y%m%dT%H%M%SZ)-$(git rev-parse --short HEAD)"
export RELEASE_ID
export NODE_ENV=production
export PUBLIC_URL="/releases/${RELEASE_ID}/3dviewer/"
export APP_CONFIG=config/standalone.js
export QUICK_BUILD=false

yarn workspace @ohif/app build:viewer
```

Для PowerShell задать те же env-переменные синтаксисом PowerShell. Установленный bundled runtime можно использовать, если он совместим; не считать его автоматически проверенным.

Если snapshot включает незакоммиченные изменения, дополнительно записать его digest: одного SHA HEAD недостаточно для описания релиза.

### Проверка артефакта

- сборка завершилась успешно, нет подмены production результатом dev:fast;
- HTML ссылается на ресурсы `/releases/<id>/3dviewer/`;
- `app-config.js` содержит автономную конфигурацию и basename `/3dviewer/`;
- присутствуют JS/CSS, workers, WASM, нужные шрифты и изображения;
- нет `hot-update.*`, соединения с HMR websocket, серверных `.env`, реальных ключей;
- публичные sourcemap исключены из deploy-артефакта;
- старый service worker не возвращает предыдущие HTML/config и не вызывает внешние запросы;
- все нужные assets приложения доступны с его собственного origin.

В текущем production Webpack InjectManifest закомментирован; отдельно проверить фактический `init-service-worker.js` и старые регистрации. Не удалять service workers других приложений браузера глобальным скриптом.

## 10. Подготовка VPS

До изменений проверить, что подключение ведёт на нужный отдельный VPS, а не на основной сервер проекта:

```bash
hostnamectl
uname -m
free -h
df -h
ss -lntp
```

На новом сервере установить Nginx и необходимые инструменты:

```bash
sudo apt-get update
sudo apt-get install -y nginx ca-certificates curl rsync unzip
```

Настроить пользователя `deploy` с SSH-ключом и достаточными правами для размещения релизов. Не отключать существующий SSH-вход до проверки второго подключения. Если включается firewall, сначала разрешить фактический SSH-порт.

Для этого этапа не открывать наружу 8080 и не требовать открытия 80/443. Nginx слушает loopback, доступ идёт через SSH. Удаление или изменение других vhosts и служб допустимо только после проверки, что они действительно относятся к новому тестовому VPS и не используются.

Создать каталоги:

```bash
sudo install -d -o deploy -g www-data -m 2750 /var/www/orbital-viewer
sudo install -d -o deploy -g www-data -m 2750 /var/www/orbital-viewer/releases
```

Проверить, что Nginx работает от ожидаемого пользователя/группы. Файлы релиза должны читаться Nginx. Не использовать `chmod 777`.

Не устанавливать Node/Puppeteer, БД, Redis, Orthanc или серверный генератор панорам. На VPS нет необходимости хранить исследования. Ограничить логи и контролировать место под релизы.

## 11. Nginx для автономного теста

Создать отдельный site-конфиг, например `/etc/nginx/sites-available/orbital-viewer-stage1`. Проверить подключение через `sites-enabled` по правилам текущего Nginx. Все пути и версия Nginx должны быть сверены на VPS.

### Общие заголовки

Файл `/etc/nginx/snippets/orbital-viewer-headers.conf`:

```nginx
add_header Cross-Origin-Opener-Policy "same-origin" always;
add_header Cross-Origin-Embedder-Policy "require-corp" always;
add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "no-referrer" always;
add_header X-Frame-Options "DENY" always;
```

### Site-конфиг

```nginx
server {
    listen 127.0.0.1:8080;
    server_name localhost 127.0.0.1;

    root /var/www/orbital-viewer/current;
    index index.html;
    autoindex off;

    include /etc/nginx/snippets/orbital-viewer-headers.conf;
    add_header Cache-Control "no-cache";

    access_log /var/log/nginx/orbital-viewer-stage1.access.log;
    error_log /var/log/nginx/orbital-viewer-stage1.error.log warn;

    gzip on;
    gzip_vary on;
    gzip_comp_level 4;
    gzip_min_length 1024;
    gzip_types text/css application/javascript application/json application/wasm image/svg+xml;

    location = /healthz {
        default_type text/plain;
        return 200 "ok\n";
    }

    location = /build-info.json {
        try_files $uri =404;
        include /etc/nginx/snippets/orbital-viewer-headers.conf;
        add_header Cache-Control "no-store" always;
    }

    location ~ (^|/)\. {
        return 404;
    }

    location ~* \.(?:env|ini|log|sql|bak|map)$ {
        return 404;
    }

    location = / {
        return 302 /3dviewer/;
    }

    location = /3dviewer {
        return 301 /3dviewer/$is_args$args;
    }

    location = /3dviewer/index.html {
        try_files $uri =404;
        include /etc/nginx/snippets/orbital-viewer-headers.conf;
        add_header Cache-Control "no-store" always;
    }

    location = /3dviewer/app-config.js {
        try_files $uri =404;
        include /etc/nginx/snippets/orbital-viewer-headers.conf;
        add_header Cache-Control "no-store" always;
    }

    # Точный порядок regex сохранять: исключения перед общим правилом релиза.
    location ~ "^/releases/[A-Za-z0-9_-]+/3dviewer/(?:index\.html|app-config\.js)$" {
        root /var/www/orbital-viewer;
        try_files $uri =404;
        include /etc/nginx/snippets/orbital-viewer-headers.conf;
        add_header Cache-Control "no-store" always;
    }

    location ~ "^/releases/[A-Za-z0-9_-]+/3dviewer/" {
        root /var/www/orbital-viewer;
        try_files $uri =404;
        include /etc/nginx/snippets/orbital-viewer-headers.conf;
        add_header Cache-Control "public, max-age=31536000, immutable";
    }

    location /releases/ {
        return 404;
    }

    # Отсутствующий JS/WASM/worker не должен получать HTML с кодом 200.
    location ~* ^/3dviewer/.*\.(?:js|mjs|css|wasm|json|png|jpg|jpeg|svg|ico|woff|woff2|ttf|bin|onnx|data|webmanifest)$ {
        try_files $uri =404;
    }

    # F5 на клиентском маршруте возвращает оболочку приложения.
    location /3dviewer/ {
        try_files $uri $uri/ /3dviewer/index.html;
    }

    location / {
        return 404;
    }
}
```

Проверить подключение `mime.types` в общем Nginx config: JS должен иметь JavaScript MIME, WASM — `application/wasm`, CSS — `text/css`.

В locations с собственным `add_header` общий include повторяется намеренно: иначе на распространённых версиях Nginx родительские `add_header` перестают наследоваться. Не добавлять новые директивы из свежей документации без проверки их поддержки установленным пакетом.

В шаблоне нет proxy_pass, S3/API-маршрутов, приёма файлов, сертификатов и привязки к домену.

Применение:

```bash
sudo nginx -t
sudo systemctl reload nginx
ss -lntp
curl --fail --silent --show-error http://127.0.0.1:8080/healthz
```

Подтвердить, что 8080 слушает **только** `127.0.0.1`, а не `0.0.0.0`. При ошибке конфига не выполнять restart работающего Nginx вслепую.

## 12. Перенос и публикация релиза

Перенести архив и checksum на VPS по SSH/SCP/rsync. Проверить checksum до распаковки. Распаковывать собственный проверенный артефакт пользователем deploy в новый каталог, не поверх текущего.

Итог:

```text
/var/www/orbital-viewer/
  releases/
    <RELEASE_ID>/
      3dviewer/
        index.html
        app-config.js
        ...
      build-info.json
  current -> /var/www/orbital-viewer/releases/<RELEASE_ID>
```

Релиз после публикации неизменяемый. Исправление получает новый release ID и новый PUBLIC_URL. Файлы доступны группе Nginx на чтение; не наследовать неожиданные UID и права из архива.

Проверить до переключения:

- release ID имеет согласованный формат без `/`, пробелов и shell-фрагментов;
- `index.html`, `app-config.js` и все необходимые assets существуют;
- Nginx может прочитать каталог;
- `current` отсутствует или является ожидаемой symlink; если там обычный каталог/чужая ссылка, разобраться до замены;
- временная ссылка для этого ID ещё не существует.

Пример атомарного переключения как deploy, с остановкой при любой ошибке:

```bash
set -e
VIEWER_ROOT=/var/www/orbital-viewer
RELEASE_PATH="$VIEWER_ROOT/releases/$RELEASE_ID"

test -f "$RELEASE_PATH/3dviewer/index.html"
test -f "$RELEASE_PATH/3dviewer/app-config.js"
test ! -e "$VIEWER_ROOT/.current-$RELEASE_ID"
test ! -L "$VIEWER_ROOT/.current-$RELEASE_ID"
ln -s "$RELEASE_PATH" "$VIEWER_ROOT/.current-$RELEASE_ID"
mv -Tf "$VIEWER_ROOT/.current-$RELEASE_ID" "$VIEWER_ROOT/current"
```

Выполнять после указанных проверок и задания фактического `RELEASE_ID`. При первом запуске предыдущего релиза ещё нет; это отразить в отчёте. При обновлении сохранить его путь для отката.

Смена только symlink не требует restart Nginx. Проверить `/build-info.json`, актуальный index и доступность ресурсов релиза.

Старые релизы сразу не удалять: открытые вкладки могут запрашивать их chunks/worker/WASM. Размер retention выбрать после измерения артефакта и свободного места. Не допускать заполнения 30 ГБ логами/релизами; не удалять чужие каталоги или текущий релиз.

## 13. Подключение с рабочего компьютера

Туннель запускается **на компьютере, где будет открыт браузер**, а не внутри VPS. Нужен установленный SSH-клиент и разрешённый local forwarding.

Шаблон команды, одинаковый по смыслу для Windows OpenSSH и Linux/macOS:

```text
ssh -N -T -p <SSH_PORT> -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -L 127.0.0.1:18080:127.0.0.1:8080 <SSH_USER>@<VPS_IP>
```

Все `<...>` заменить реальными значениями до запуска. Приватный ключ при необходимости задаётся через существующий SSH config/agent или `-i` с локальным путём. Не копировать приватный ключ на VPS и не отключать проверку host key; сверить fingerprint при первом подключении.

Пока туннель работает, открыть:

```text
http://localhost:18080/3dviewer/
```

Также проверить:

```text
http://localhost:18080/healthz
http://localhost:18080/build-info.json
```

Локальный порт 18080 выбран как пример. Если он занят, выбрать другой свободный loopback-порт и записать итоговый адрес. Не привязывать локальную сторону туннеля к `0.0.0.0`.

При разрешении `localhost` в IPv6 и ошибке подключения проверить `http://127.0.0.1:18080/3dviewer/`: loopback IP тоже поддерживается как потенциально доверенный origin. Выбрать один рабочий адрес для всей приёмки и записать его.

Проверить в DevTools:

```js
window.isSecureContext
window.crossOriginIsolated
typeof SharedArrayBuffer
```

Ожидается `true`, `true`, `"function"` в поддерживаемом браузере. Если результат другой, проверить localhost, заголовки HTML, политики браузера, workers и загрузку ресурсов; не маскировать причину отключением безопасности.

Закрытие SSH-туннеля прекращает дальнейшее получение ресурсов с VPS. Уже загруженное локальное исследование может продолжать отображаться, но это не полноценная offline-приёмка.

## 14. Функциональная проверка

Тестировать на разрешённых локальных копиях DICOM. Выбор локального файла или папки не должен загружать их на VPS. Не размещать реальные исследования в webroot для удобства проверки.

Рекомендуемый набор: небольшое исследование, типовая КЛКТ, большое ЛОР-поле, поддерживаемые сжатые и несжатые DICOM. Не менять оригиналы; использовать копии.

### Запуск и локальное открытие

- [ ] Входной адрес открывает локальную стартовую страницу, не S3 Explorer и не кабинет.
- [ ] Работают «Локальные файлы», «Локальная папка», существующий drag-and-drop.
- [ ] После выбора серии открывается нужный стоматологический режим.
- [ ] Во время открытия нет запросов к CRM/S3/стороннему PACS и нет POST с DICOM.
- [ ] В Browser Network загружаются ресурсы с localhost через VPS; у них нет HMR websocket.
- [ ] При ошибке файла показано понятное состояние, нет бесконечного spinner.
- [ ] Второе исследование не получает данные/панораму первого.

### Изображение и инструменты

- [ ] Пациент, серия, порядок срезов, ориентация и масштаб корректны.
- [ ] MPR, прокрутка, крест и 3D работают как в текущей локальной версии.
- [ ] Окна разворачиваются и возвращаются в раскладку.
- [ ] Линейки и углы работают; точки замеров сохраняют ожидаемое поведение при смене среза.
- [ ] Инструмент канала и импланты доступны.
- [ ] Импланты ориентируются по плоскости; установка завершается; перенос и удаление работают.
- [ ] Стартовая автопанорама строится, переключается с черепом и разворачивается.
- [ ] Редактор получает готовый результат; повторное открытие не запускает ненужный полный расчёт.
- [ ] Правка дуги, толщина/высота, резкость и пропорциональное вписывание работают.
- [ ] Горизонтальная и вертикальная линии панорамы отображаются и перемещаются.
- [ ] Ошибка автоматического поиска дуги обрабатывается штатно, доступен существующий ручной сценарий.

### Браузерные ресурсы

- [ ] JS/CSS/worker/WASM доступны, имеют корректный MIME.
- [ ] Нет ошибок COOP/COEP, SharedArrayBuffer и Worker.
- [ ] `window.isSecureContext` и `window.crossOriginIsolated` равны true.
- [ ] В свежем профиле браузера работает та же сборка без зависимости от старого dev-cache.
- [ ] Проверены выбранные актуальные браузеры на Windows, их версии записаны.

При F5 внутри режима локальные файлы могут потребовать повторного выбора: browser-local состояние не обязано переживать перезагрузку. Это не серверный 404. Проверять, что Nginx отдаёт оболочку приложения и пользователь может открыть файлы повторно, а не требовать несуществующего сохранения DICOM на сервере.

## 15. Проверки VPS, обновления и отката

### HTTP и эксплуатация

- [ ] Nginx слушает только loopback 8080; доступ проверен через SSH-туннель.
- [ ] `/healthz` даёт 200, но отдельно проверены настоящий index и ресурсы.
- [ ] F5 на клиентском маршруте не даёт Nginx 404.
- [ ] Отсутствующий JS/WASM получает 404, а не HTML с 200.
- [ ] `.env`, `.map` и dotfiles не выдаются.
- [ ] На VPS не работают dev-server/Node и нет постоянных ключей S3.
- [ ] После перезапуска VPS Nginx доступен; после нового SSH-туннеля просмотрщик открывается.
- [ ] Настроена ротация логов; измерены размер релиза и свободный диск.

### Обновление

Подготовить второй тестовый релиз с другим ID, без изменения логики инструментов:

1. Открыть первую сборку и локальное исследование.
2. Опубликовать второй релиз и переключить `current`.
3. Проверить новый вход и `build-info.json`.
4. В старой вкладке проверить ленивую загрузку ресурсов/инструментов: URLs первого релиза должны оставаться доступны.
5. Убедиться в отсутствии смешивания нового HTML и старого app-config.

### Откат

Сохранить путь первого релиза и атомарно вернуть на него `current` тем же проверенным способом. Проверить build-info, новую вкладку и локальное открытие DICOM. Каталоги второго релиза не удалять немедленно: они могут использоваться открытыми вкладками.

Не откатывать весь рабочий каталог через `git reset --hard`; не менять другие серверы. Если рабочего предыдущего релиза ещё нет, откат первой публикации означает отключение только созданного тестового site-конфига/маршрута с сохранением артефакта и логов для разбора.

## 16. Измерения первого этапа

Зафиксировать:

- размер production-артефакта и установленного релиза;
- время загрузки приложения через туннель;
- время локального открытия типовой серии;
- время готовности MPR и автопанорамы;
- CPU/RAM VPS при раздаче приложения;
- CPU/RAM браузера и характеристики тестового компьютера;
- свободный диск VPS до и после двух релизов;
- ошибки и версии проверенных браузеров.

Не делать вывод о скорости S3, готовности CRM или возможности 30 одновременных сетевых открытий: на этом этапе такие сценарии не проверяются. Проверка через один SSH-туннель не является оценкой скорости будущего публичного HTTP-доступа.

Если требуется тест нескольких пользователей, каждый получает ресурсы приложения и открывает свои локальные DICOM. Нагрузка на раздачу статики и расчёты в браузерах должны измеряться отдельно. Не превращать это в тест хранилища.

Существующие unit-тесты затронутых маршрутов/конфигурации и стоматологических модулей запускать подходящим способом. Пример команды из корня, синтаксис сверить с установленным Jest:

```bash
yarn jest --config extensions/cornerstone/jest.config.js \
  --runInBand --coverage=false \
  --testPathPattern='ManualPanorama|DentalMeasurementTools|DentalImplantTool|implantGeometry|dentalGeometry'
```

Не отмечать тесты пройденными, если они не запускались или запускались на другой сборке.

## 17. Результат, который Cursor должен передать

1. Список выполненных изменений только в просмотрщике и новом VPS.
2. Diff автономной конфигурации и минимальных изменений UI/роутинга.
3. Воспроизводимую сборку: инструменты, source snapshot, release ID, checksum.
4. Архив релиза, его размер и расположение на VPS.
5. Фактический Nginx-конфиг и способ переключения/отката.
6. Рабочую команду SSH-туннеля без секретов и адрес открытия.
7. Заполненную приёмку с результатами и измерениями.
8. Явный список оставшихся проблем; при отсутствии доступа — границу реально выполненной работы.
9. Подтверждение границ: основной сервер, S3, CRM и DNS не менялись.

Итог первого этапа: **проверенная автономная production-сборка приходит с VPS и полноценно открывает локальные исследования в браузере.** После передачи этого результата не переходить к следующим этапам.

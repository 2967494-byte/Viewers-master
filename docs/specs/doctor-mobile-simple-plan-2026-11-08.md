# ORBITAL Doctor: простой поэтапный план подключения к CRM

Дата: 8 ноября 2026. Статус: согласованное направление, план реализации. Новые мобильные API пока не объявляются работающими. Этот документ заменяет расширенные схемы сопряжения от 8 ноября в части авторизации, скачивания, кеширования и офлайн-разрешений. Функциональность кабинета и уже сделанный локальный viewer сохраняются.

## 1. Что делаем

Приложение входит в существующую CRM как врач по отдельному токену устройства, получает его пациентов и исследования. При входе на экран запрашивает свежие данные. По действующему праву скачивает уже подготовленные сжатые серии из S3 и открывает их собственным локальным viewer.

### Принятая политика хранения

| Данные | Правило |
| --- | --- |
| Обычное открытое исследование | После полной загрузки кешируется на 24 часа |
| Явно сохранённое исследование | Остаётся на устройстве до ручного удаления |
| Сохранённый проект с измерениями/планированием | Закрепляет также локальные файлы исследования, чтобы очистка кеша не оставила проект без снимка |
| Отзыв прав / удаление исследования из HOT | Запрещает новые серверные действия; уже скачанные копии продолжают открываться по локальной политике хранения |
| Отсутствие сети | Доступны сохранённые списки и локальные исследования; изменения на сервер не отправляются |

24 часа отсчитываются от **завершения загрузки**, а не от последнего просмотра. «Сохранить на устройстве» закрепляет тот же набор без повторной загрузки и без второй копии. Закреплённые исследования не очищаются автоматически ради освобождения места.

Очистка просроченного кеша выполняется при запуске/возвращении приложения и открытии библиотеки. iOS не гарантирует запуск удаления ровно через 24 часа в закрытом приложении: физическая очистка выполняется при следующей возможности. Если просроченный незакреплённый набор сейчас открыт в viewer, его очистка откладывается до закрытия. Закреплённые наборы при закрытии не удаляются. «Удалить с устройства» действительно удаляет файлы; при наличии проекта интерфейс предупреждает о последствиях.

## 2. Что упрощаем

- Используем существующие сжатые DICOM, `manifest.json` и `ohif_metadata.json`.
- Приложение получает временные GET-ссылки и **только читает S3**. Для этого подключения не добавляем PUT в S3.
- Новый `download-inventory.json`, backfill, мобильная публикация в БД, ES256/offlineGrant и отдельная download-сессия на сервере в первый выпуск не входят.
- Компрессор, его lease/SAVEPOINT и текущую веб-публикацию ради приложения не меняем.
- Один отзываемый токен устройства, без refresh-токенов, сложной ротации и зашифрованного replay-cache.
- Списки обновляются обычными запросами. Фоновую постоянную синхронизацию, WebSocket, очередь офлайн-изменений и новый Uploader не добавляем.

Большие файлы идут S3 → iPhone; CRM передаёт списки, статусы и ссылки. Медицинский viewer поставляется внутри приложения и при локальном открытии не загружает сайт CRM.

## 3. Минимальная авторизация

1. Врач в своём веб-кабинете нажимает «Подключить приложение» и получает QR на 120 секунд.
2. В QR: доверенный адрес сервера, одноразовый случайный билет и срок. Постоянного пароля нет.
3. Приложение обменивает билет на случайный `accessToken`, сохраняет токен в Keychain и получает подтверждённую сервером учётку врача.
4. Для пилота токен действует **30 суток от привязки**, срок настраивается на сервере. По истечении для новых серверных запросов нужен новый QR; автоматическое продление можно добавить позже.
5. На каждом запросе сервер проверяет токен, срок, отзыв, блокировку и подтверждение пользователя, текущую привязку Doctor и `User.session_version`. Смена пароля/сброс сессий прекращают серверный доступ.
6. Права пациентов и исследований берём из текущей CRM. Для скачивания готового 3D дополнительно требуется существующее `online_viewer_enabled` и включённый viewer. Отсутствие этого права не должно выглядеть как исчезновение всех пациентов.
7. Врач может отключить устройство из веб-кабинета. Приложение может отозвать собственный токен при выходе.

На сервере достаточно двух небольших моделей: одноразовые QR-билеты и токены устройств (в БД только хеши секретов). Атомарный обмен одного билета, разумное ограничение попыток и проверка владельца устройства сохраняются. Потерянный ответ обмена QR решаем понятным повторным сканированием **нового** QR, без replay-cache с открытыми токенами.

Обычный браузер продолжает работать через свою сессию. Мобильный токен определяет пользователя в контексте мобильного запроса; существующие правила доступа используются для этого пользователя. Не подставлять врача из request body, не обходить ACL, не переписывать весь веб-контур. Способ интеграции с текущей авторизацией выбирать после точечной проверки app factory; тест должен исключить подмену mobile Bearer чужой browser cookie.

Пилот — персональные аккаунты врачей, включая врачей-кураторов с их текущими правами. Аккаунт клиники получает понятное сообщение о неподдерживаемом типе, а не пустую ленту.

## 4. Обновление экранов

- При запуске/возвращении на главный экран — запрос актуальных данных главной.
- При входе в «Пациенты» — актуальный список; поиск и страницы запрашиваются у CRM.
- При открытии пациента — актуальный список его исследований.
- Ручное обновление потягиванием вниз.
- Одновременные одинаковые запросы объединяются; постоянного polling нет.
- При недоступной сети остаются последние сохранённые данные с отметкой времени обновления. Сетевой сбой не завершает вход и не удаляет снимки.
- При 401 приложение предлагает обновить подключение по QR. Свои локальные копии можно продолжать просматривать; завершившаяся онлайн-сессия не является таймером удаления локальных файлов.

Статусы сервера и устройства независимы. Например, «На устройстве» остаётся доступным, даже если в CRM готовая серия больше недоступна. Успешная загрузка/удаление сразу обновляет локальную карточку; отдельная серверная синхронизация факта наличия копии на телефоне для первого выпуска не нужна.

Явный выход закрывает медицинские экраны учётки. Сохранившиеся файлы изолированы по serverId/userId и вновь доступны только той же учётке после подключения; другой врач не получает их. При обычном офлайн-запуске приложение использует ранее подтверждённый локальный профиль, без сетевого запроса и без Demo-подмены.

## 5. Минимальные API — проект для реализации

База: `https://admin.orbital3d.ru/api/doctor-mobile/v1`. Новые маршруты ниже ещё требуется реализовать. Старый расширенный OpenAPI с refresh/offlineGrant **не является контрактом этого выпуска**. Namespace можно сохранить, поскольку его прежняя версия не была объявлена развёрнутым мобильным API.

| Метод и путь | Что делает |
| --- | --- |
| `POST /pairings` | Создать QR из авторизованного веб-кабинета врача, с CSRF |
| `POST /pairings/exchange` | Обменять одноразовый билет на токен устройства |
| `GET /me` | Получить врача, serverId, права и срок токена |
| `DELETE /sessions/current` | Отозвать текущий токен устройства |
| `GET /patients?search=...&cursor=...&limit=...` | Получить разрешённых пациентов |
| `GET /studies?patientId=...&cursor=...&limit=...` | Получить разрешённые исследования и готовность 3D |
| `GET /studies/{studyId}` | Актуальная карточка конкретного исследования |
| `POST /studies/{studyId}/downloads` | Проверить доступ и выдать GET-ссылки на готовое поколение |

Операции me/sessions/patients/studies требуют Bearer. Создание QR использует browser session + CSRF, а exchange — одноразовый билет. Ошибки — JSON, без HTML login redirect. `401` — нужно подключение; `403` — нет права операции; `404` — исследование отсутствует/недоступно; `409` — серия готовится или изменилась; `410` — облачный набор истёк. Для персональных данных и токенов — `Cache-Control: no-store`.

Билет обмена: `pairingTicket`, `deviceId`, `deviceName`, `appVersion`. Ответ: `accessToken`, `expiresAt`, `me`. `me` включает `userId`, `doctorId`, `serverId`, `displayName`, `canUseViewer`; ID передаются строками. Клиент не задаёт doctorId для выбора чужой учётки. Доверенный origin пилота — только `https://admin.orbital3d.ru`.

Списки возвращают `items`, опциональный `nextCursor` и `serverTime`. В исследованиях нужны собственные `studyId`/`patientId`, дата, название, центр, готовность viewer, `canDownload`, текущие sourceVersion/representationId/profileVersion/generationId, если серия ready. Поля, которых пока нет в API, не заполняются данными Demo.

`POST /studies/{studyId}/downloads` принимает `expectedSourceVersion` и `expectedGenerationId`, взятые из карточки. Ответ содержит:

```json
{
  "studyId": "example-study",
  "patientId": "example-patient",
  "sourceVersion": "example-source",
  "representationId": "jpeg2000-20x",
  "profileVersion": 1,
  "generationId": "example-generation",
  "urlsExpiresAt": "2026-11-08T12:15:00Z",
  "files": [
    {"path": "manifest.json", "downloadUrl": "https://storage.example.invalid/manifest.json"},
    {"path": "series-1/ohif_metadata.json", "downloadUrl": "https://storage.example.invalid/index.json"},
    {"path": "series-1/instances/000001.dcm", "downloadUrl": "https://storage.example.invalid/000001.dcm"}
  ]
}
```

Это иллюстративный, не рабочий ответ. `files` включает существующий manifest, индексы и все DICOM опубликованного поколения; mutable representations.json для локального открытия не нужен. Пути относительные от generation-root. Число срезов/серий берётся из manifest и индексов.

Для подписания повторно используем существующую проверку готовой сжатой серии и точных S3-ключей веб-просмотрщика, выделяя небольшой общий helper при необходимости. Старый cookie resolver не объявляем новым мобильным endpoint. Сервер не читает сотни DICOM и не делает HEAD каждого файла ради ответа. Ссылки ограничены доступностью текущего облачного поколения; клиент не присылает bucket/key/произвольный S3 prefix.

При истечении ссылок клиент повторяет тот же запрос downloads. Если поколение прежнее — использует новые ссылки и догружает недостающие файлы. Если изменилось — `409 source_changed`, обновление карточки и новая отдельная загрузка. Серверной таблицы download grants и идемпотентных записей для этой операции нет: она проверяет доступ и выдаёт ссылки, не меняя данные.

## 6. Локальное хранение и viewer

Один физический набор файлов и небольшая запись о нём:

```text
serverId / userId / studyId / generationId
sourceVersion, representationId, profileVersion
localPath, downloadedAt, cacheExpiresAt, isSaved, actualBytes, status
```

- Использовать уже работающий локальный раздатчик, ограничив его конкретным выбранным набором.
- У каждого пациента своё исследование и свой путь. Общий `realVatechStudyPrefix`, фиксированная sourceVersion и fallback к другому встроенному исследованию убираются из обычного открытия.
- Скачивание идёт во временную папку. Ready появляется после успешной загрузки полного состава manifest/индексов/DICOM и проверки их связности. Сетевой прогресс не рисуется таймером.
- Показать реальные полученные байты и число файлов. Пока общий размер неизвестен, честная надпись «152 из 450 файлов, 8.3 МБ» предпочтительнее выдуманного процента. Не добавлять инвентаризацию всего HOT только ради процента.
- Прерванное скачивание догружает отсутствующие файлы целиком; сложное побайтовое Range/resume не требуется для первого выпуска. Чужие/неполные поколения не смешиваются.
- «Сохранить на устройстве» выставляет `isSaved=true` и исключает набор из очистки кеша. Если набора ещё нет, сначала выполняется обычная загрузка и затем закрепление.
- Локальные проекты привязаны к user/study/generation; измерения и импланты не переносятся между пациентами или поколениями автоматически. При смене серии прежний render-state очищается.
- В native local mode срок `expiresAt` облачного manifest не запрещает открывать сохранённую копию. Облачный loader продолжает проверять HOT-сроки; не изменять даты в скачанном manifest ради обхода.
- Содержимое приватной библиотеки не раздаётся в сеть, не публикуется целиком в Files и не попадает в резервную копию iCloud. Токен CRM не передаётся JS viewer или S3.

## 7. Этапы: по одной проверяемой сборке

Не начинать заново уже сделанные MPR/панораму/измерения и дизайн. Ни один этап ниже не считается выполненным самим написанием этого плана. По завершении этапа передать сборку/исходники, короткую инструкцию проверки и остановиться до отзыва владельца. Xcode/iPhone проверяет агент на Mac или пользователь; Windows-проверка исходников не является сборкой iOS.

### S01 — свои снимки и простая локальная библиотека

**Где:** iOS. Сервер не нужен.

Убрать общий путь исследования и имитацию сохранения. Ввести LocalStudyStore, отдельные каталоги, реальную запись состояния, кеш 24 часа, закрепление/удаление и фактический размер. Связать сохранение проекта с закреплением снимка. Для проверки использовать два разных локальных набора; импорт через Files — явно тестовый путь, не подмена настоящего скачивания.

**Проверка сборки:** пациент A и B показывают разные серии; A → B → A не смешивает проекты. Незакреплённый кеш старше суток очищается, закреплённый остаётся. Дату старения моделировать через тестовые записи/часы, не менять системное время iPhone. После завершения процесса обе допустимые локальные копии открываются в авиарежиме. Нет файлов — нет статуса ready.

### S02 — QR и настоящий врач

**Где:** небольшой серверный модуль + iOS.

На сервере две модели QR/device token и четыре auth-операции из §5, кнопка QR и отзыв устройства в веб-кабинете. На iOS — сканер, Keychain, показ реального профиля `/me`, повторное подключение по истечении/отзыве. Проверить границы namespace, CSRF, срок и одноразовость QR. Добавить описание разрешения камеры. Один отключаемый флаг нового mobile API; существующий web viewer работает как раньше.

**Проверка сборки:** QR → реальный врач в профиле; перезапуск сохраняет подключение. Чужая cookie не меняет врача токена. Отзыв/смена пароля блокируют серверные запросы, свои локальные снимки сохраняются. Другой врач не видит локальную библиотеку предыдущего.

### S03 — реальные пациенты и обновление экранов

**Где:** сервер + iOS.

Подключить `/patients`, `/studies`, карточку исследования и главную на основе доступных данных. Тонкие JSON-маршруты используют текущие правила CRM. Не объединять это с массовым рефакторингом веб-ACL. Новые и существующие проверки сверить на own/shared/куратор/история пациента. Добавить поиск/пагинацию и обновление при входе на экраны по §4. Сетевой сбой оставляет последние данные с понятной отметкой.

**Проверка сборки:** два врача видят ровно свои разрешённые данные; подстановка чужого studyId не открывает карточку/скачивание. В CRM изменён список → после входа на экран он обновился. Нет дублей между страницами. Offline показывает прошлый список без подмены Demo.

### S04 — настоящее скачивание из существующего S3

**Где:** одна серверная операция downloads + iOS downloader/local adapter.

Выдать ссылки только на уже готовую сжатую серию. На iOS заменить Timer реальной загрузкой, передать полный точный путь/версию в viewer, показать настоящий прогресс, открыть локально и кешировать на сутки. При закреплении сохранить до ручного удаления. Не добавлять inventory, пересжатие, S3 PUT, новые worker и серверные download-grant таблицы.

**Проверка сборки:** два выбранных владельцем реальных исследования скачиваются и открываются каждое в своей карточке, включая панораму из собственной серии. Полностью завершить приложение, включить авиарежим, открыть повторно. Проверить обрыв сети, истечение ссылок, смену поколения, нехватку места и отмену. Уже загруженные копии открываются после отзыва серверного доступа; новые скачать нельзя. Закреплённая копия открывается даже после удаления её облачного поколения.

### S05 — короткий пилот и выпуск

**Где:** реальный iPhone + тестовый/ограниченный серверный доступ.

Проверить все предыдущие сценарии, очистку суток, несколько сохранённых исследований, память и скорость на большом 16×16. Сжатие экономит сеть/диск, а декодированный объём всё ещё требует память. Исправить найденные ошибки и затем включать небольшой группе врачей. Перед выкладкой пройти тесты существующего web viewer; миграции только добавочные, mobile-флаг изначально выключен, обработка очереди компрессора не меняется.

**Готовность:** QR → актуальные пациенты → настоящий download → свой viewer → повторное открытие офлайн; предсказуемые кеш/закрепление/удаление и отсутствие доступа между учётками. Без этого основного сценария остальные функции не объявляются подключёнными к бою.

## 8. Остальной кабинет после первого сопряжения

Полное ТЗ остаётся ориентиром. После S05 подключать небольшими отдельными сборками: документы/заключения и заметки; запись пациентов; направления; сообщения/уведомления и остальные настройки. Каждая операция использует тот же токен и существующие бизнес-правила CRM. Для первого выпуска серверные изменения выполняются при наличии сети; универсальная синхронизация офлайн-правок не требуется. Уже реализованное локальное сохранение проекта остаётся автономным.

## 9. Какие старые материалы теперь исторические

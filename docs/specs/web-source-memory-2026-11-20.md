# Первый этап оптимизации памяти веб-просмотрщика — 20 ноября 2026

Изменения локальные. Боевой дистрибутив и переданные Windows-установщики не перезаписывались.

## Что изменено

После готовности пикселей поддерживаемого однослойного S3-изображения в объёме удаляется image.data и освобождаются записи исходного файла/датасета в загрузчике. Пиксельный массив и image cache Cornerstone остаются: текущий image-backed volume читает их непосредственно. Для stack, многокадровых и неподдерживаемых форматов остаётся прежний lifecycle. Кэш не удаляется целиком, разрешение и графический профиль не изменяются. Первая картинка, загруженная заранее для метаданных, сохраняет прежний lifecycle: в тесте остаётся один исходный файл вместо 750.

## Локальный A/B замер

Electron 43.4.0, объём 800×800×750, два одинаковых неминифицированных билда; контроль отличается только отключением новой очистки. Для обоих способов подачи файлов выполнен по одному полному открытию в каждом билде. Принудительный GC перед замером renderer; процессы и ОС не полностью изолированы. Это не статистически устойчивый бенчмарк скорости или гарантированная экономия свободной RAM.

| Источник / вариант | Renderer working set, МиБ | Browser working set, МиБ | Удерживаемые исходные DICOM в renderer, МиБ |
|---|---:|---:|---:|
| Распакованные — До | 2339.2 | 1094.9 | 916.3 |
| Распакованные — После | 1501.7 | 112.8 | 1.2 |
| JPEG2000 — До | 1390.2 | 128.5 | 10.0 |
| JPEG2000 — После | 1314.3 | 114.1 | 0.0 |

Пиксельный image cache везде 915.5 МиБ — он нужен для работы объёма. Видеопамять текстуры этим изменением не сокращается; working set GPU-процесса нельзя считать размером VRAM. Суммирование working set процессов также не равно свободной физической памяти: возможны общие страницы.

В сценарии обычного веба со сжатыми файлами наблюдалось около 90 МиБ снижения working set двух CPU-процессов, но детерминированно устранённые parsed-source буферы составляют около 10 МиБ; остальное включает Blob, объекты и вариативность GC/аллокаций. Нельзя переносить большой выигрыш распакованных файлов на все веб-исследования. В распакованном сценарии parsed-source буферы сократились с 916.3 до 1.2 МиБ.

## 21 ноября: отдельная очередь декодирования и ограничение работников

Изменения локальные, основной дистрибутив и установщики не перезаписывались. Проверочный веб: `tmp/web-decode-budget-20261121/optimized`. Контроль: соседняя папка `control`. Оба варианта включают одинаковую описанную выше очистку исходных файлов, полный исходный объём и одинаковый рендер. Новое сравнение измеряет только дополнительный эффект очереди и числа работников; предыдущую экономию очистки повторно к нему не прибавлять.

Общая функция `orbitalDecodeBudget.ts` согласует число работников DICOM и S3-декодирований: один при сообщаемой памяти до 4 ГБ или числе логических процессоров до четырёх, два в остальных случаях, с учётом меньшего ограничения конфигурации. До двух/четырёх полных конвейеров соответственно позволяют скачивать следующий сжатый файл заранее, но разбор DICOM и декодирование начинаются только после получения отдельного слота. Это ограничение временной работы, не изменение разрешения, slope/intercept, типов исходных пикселей или бюджета текстуры.

Очередь учитывает изменение лимита во время работы, отменяет ожидающие задачи и освобождает слот после ошибки. Счётчики доступны по `window.__orbitalImageTaskStats()` без таймеров и дополнительных сетевых отчётов. Проверки app/core: 13 тестов, включая реальное ограничение вызовов декодера на слабом профиле, опережающее скачивание, отмену ожидающего декодирования, совместное использование файла, повторный запрос и сохранение пикселей.

### A/B: сжатый полный объём 800 × 800 × 750

Electron 43.4.0, текущий компьютер разработки. Четыре чередующихся прогона обычного профиля (два на вариант) и одна пара слабого профиля. В app-config стенда до запуска загрузчика переопределены только сообщаемые navigator.deviceMemory/hardwareConcurrency: 8 ГБ/16 потоков либо 4 ГБ/4 потока. Это **не ограничение физической памяти и не эмуляция процессора старого ноутбука**. Проверяется фактическое число созданных работников (3 → 2 либо 3 → 1).

| Профиль / вариант | Открытие, с | Renderer working set после GC, МиБ | Peak working set renderer, МиБ |
| --- | ---: | ---: | ---: |
| Обычный, контроль (среднее двух) | 9,50 | 1357,2 | 1475,2 |
| Обычный, новая очередь (среднее двух) | 10,94 | 1275,4 | 1398,0 |
| Слабый, контроль (один прогон) | 11,99 | 1290,3 | 1418,9 |
| Слабый, новая очередь (один прогон) | 15,55 | 1261,3 | 1361,7 |

На этих прогонах пиковая память renderer снизилась на 5,2% / 4,0%, открытие замедлилось на 15% / 30%. Память после GC вариативна; малое число прогонов не даёт статистической гарантии. Working set процесса не является полной RAM вкладки и не является свободной видеопамятью. Размер полной 3D-текстуры эта доработка не уменьшает, отказ detail-policy-limit сама по себе не устраняет. Автоматическая выкладка на бой по этим результатам не рекомендуется.

Все шесть прогонов завершили загрузку, отрисовку/навигацию, очистку image cache и volume cache, затем повторное открытие. Для каждого прогона FNV-1a проверка всех 480 000 000 значений исходных пикселей дала одинаковое значение `1965635205` (это не криптографический хеш и не клиническая валидация). Размерности и метаданные всех 750 кадров сохранены. После закрытия активных/ожидающих задач нет. Это проверка очередей и кэшей, не доказательство немедленного возврата всех внутренних WASM/браузерных аллокаций ОС.

Воспроизведение: `.scripts/build-web-memory-test.cjs optimized` с ORBITAL_WEB_BUILD_DIR; для контроля дополнительно ORBITAL_WEB_DECODE_CONTROL=1. Контрольный loader возвращает прежнее число работников и отключает отдельный слот разбора/декодирования. Запуск `.scripts/compare-web-decode-budget.cjs`. Итог: `tmp/web-decode-budget-20261121/comparison.json`. Отдельные измерения: `tmp/web-source-memory-20261120/decode-budget-*-measurement.json`. Поля аппаратного профиля и числа работников проверяются явно: нельзя выдавать неприменённый профиль за результат слабого устройства.

Отдельный сервер для проверки в обычном браузере запущен через `.scripts/start-local-web-test.cjs` с ORBITAL_LOCAL_WEB_ROOT и ORBITAL_LOCAL_WEB_DIST; адрес находится в `tmp/web-decode-budget-20261121/local-server/server.json`. Он отдаёт исходные сжатые файлы по loopback, без подмены на распакованные Windows-копии и без блочного движка.

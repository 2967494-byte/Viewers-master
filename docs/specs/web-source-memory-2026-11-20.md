# Первый этап оптимизации памяти веб-просмотрщика — 20 ноября 2026

Изменения локальные. Боевой дистрибутив и переданные Windows-установщики не перезаписывались.

## Что изменено

После готовности пикселей поддерживаемого однослойного S3-изображения в объёме удаляется image.data и освобождаются записи исходного файла/датасета в загрузчике. Пиксельный массив и image cache Cornerstone остаются: текущий image-backed volume читает их непосредственно. Для stack, многокадровых и неподдерживаемых форматов остаётся прежний lifecycle. Кэш не удаляется целиком, разрешение и графический профиль не изменяются. Первая картинка, загруженная заранее для метаданных, сохраняет прежний lifecycle: в тесте остаётся один исходный файл вместо 750.

## Локальный A/B замер

Electron 43.4.0, объём 800×800×750, два одинаковых неминифицированных билда; контроль отличается только отключением новой очистки. Для обоих способов подачи файлов выполнен по одному полному открытию в каждом билде. Принудительный GC перед замером renderer; процессы и ОС не полностью изолированы. Это не статистически устойчивый бенчмарк скорости или гарантированная экономия свободной RAM.

| Источник / вариант | Renderer working set, МиБ | Browser working set, МиБ | Удерживаемые исходные DICOM в renderer, МиБ |
|---|---:|---:|---:|
| Распакованные — До | 2339.2 | 1094.9 | 916.3 |
| Распакованные — После | 1501.7 | 112.8 | 1.2 |
| JPEG2000 — До | 1390.2 | 128.5 | 10.0 |
| JPEG2000 — После | 1314.3 | 114.1 | 0.0 |

Пиксельный image cache везде 915.5 МиБ — он нужен для работы объёма. Видеопамять текстуры этим изменением не сокращается; working set GPU-процесса нельзя считать размером VRAM. Суммирование working set процессов также не равно свободной физической памяти: возможны общие страницы.

В сценарии обычного веба со сжатыми файлами наблюдалось около 90 МиБ снижения working set двух CPU-процессов, но детерминированно устранённые parsed-source буферы составляют около 10 МиБ; остальное включает Blob, объекты и вариативность GC/аллокаций. Нельзя переносить большой выигрыш распакованных файлов на все веб-исследования. В распакованном сценарии parsed-source буферы сократились с 916.3 до 1.2 МиБ.

## Проверки

- 7 unit-тестов: очередь, отмена, повторный запрос, dedup, раннее освобождение однослойного объёма, неизменная ссылка/значения пикселей, сохранение многокадрового source.
- Полная загрузка всех 750 кадров в четырёх сценариях. Размерности и размер пиксельного кэша совпадают.
- Сравнивались 128 значений каждого из 750 кадров: контрольная сумма одинакова во всех четырёх сценариях. Это выборочная проверка, не полный хеш всех вокселей.
- Метаданные imagePlaneModule доступны для всех кадров после очистки. Масштабирование и отрисовка трёх окон после очистки прошли.
- Главный боевой app.bundle сохранён с прежним SHA256.

Код: platform/app/src/utils/decodedVolumeSource.ts и orbitalS3ImageLoader.ts. Сборка A/B: .scripts/build-web-memory-test.cjs; запуск замера: .scripts/benchmark-web-source-memory.cjs. Отчёты: tmp/web-source-memory-20261120/summary.json.

Следующая отдельная проверка — длительная работа и повторное открытие реальных сжатых серий, затем локальная проверка реального браузера перед выкладкой. Для дальнейшего крупного сокращения CPU-памяти потребуется отдельно исследовать хранение пикселей и тип данных; простое удаление image cache сломает текущий объём.

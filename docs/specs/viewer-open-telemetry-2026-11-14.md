# Статистика реального открытия ORBITAL 3D

## Что считается открытием

Запуск по `/3dviewer/v/<token>` создаёт отдельную браузерную сессию статистики. В отличие от существующего графика использованных launch-токенов, успешный результат требует всех исходных кадров открытой серии и нового завершённого нативного рендера каждого из трёх MPR-окон. Панорама, готовый интерфейс и один лишь сигнал окончания загрузки не считаются успехом.

Регистрируются время первого рендера после поступления слоёв, время полной загрузки/отрисовки, выбранный режим, фактический бюджет scalar-текстуры, исходные/отображаемые размеры, браузер и доступное имя GPU. Режим при успешном открытии сохраняется отдельно от последующих ручных переключений. Поздний context loss отражается как ошибка после открытия с сохранённым временем открытия.

Это подтверждение событий загрузчика и рендера, а не автоматическая медицинская оценка изображения. Браузер может не сообщить имя адаптера. Время включает доступ/индекс/декодирование/загрузку/рендер на клиенте, а не только сетевой трафик.

## Передача и доступ

- Только CRM token-launch; локально импортируемые снимки и автономные мобильные приложения автоматически не отправляют отчёты.
- До preflight запускается необязательный асинхронный сбор, поэтому можно зарегистрировать отсутствие WebGL 2.
- `GET /api/viewer/telemetry/config` выдаёт сессионный CSRF; `POST /sessions` создаёт UUID-сессию и принимает первую сводку; `POST /sessions/<uuid>` обновляет её.
- Владелец и приём определяются сервером по launch-токену, текущей CRM-сессии и существующему ACL. Клиент не задаёт userId/patientId/appointmentId. UUID другой учётной записи недоступен. CSRF не отключается.
- JSON ограничен 8 KiB и строгим набором полей. Не принимаются URL, DICOM UID, ФИО, пиксели, полный консольный журнал или свободный текст ошибки. Код ошибки — из конечного списка. Browser family/version извлекаются сервером из User-Agent.
- Серверная attribution позволяет администратору увидеть врача/пациента в своей CRM. Эти имена клиент не передаёт. Данные отправляются только в ту же CRM, без сторонней аналитики.
- Одно компактное состояние на открытие; обновления по этапам, не запрос на каждый срез. Монотонная sequence + row lock защищают от старого отчёта поверх нового. Повтор начального запроса идемпотентен; создание UUID сериализовано уникальным PK/SAVEPOINT. До 240 новых сессий за час на пользователя, обновление ограничено сутками.
- Сбой/отказ статистики не останавливает просмотрщик; запрос имеет таймаут. Завершение всего процесса браузера, отсутствие сети/авторизации и закрытие до первого подтверждения могут оставить неполный отчёт или не создать его. Это не считается доказанной ошибкой графики.

## Админка

На `/admin/vms` добавлен самостоятельный блок: период 1/7/30 дней до указанной даты, итоговые показатели, накопительная диаграмма результатов, разбивка режимов и 100 последних открытий. Границы дат — МСК. В карточках — среднее время первого показа и полной загрузки. Результаты без события завершения отдельно обозначены как загрузка/нет подтверждения; явное закрытие незавершённой вкладки — прервано. Они не входят в счётчик ошибок.

Прежний график оставлен и назван «Получения доступа к 3D Viewer», чтобы не смешивать исторические used_at с реальными новыми отчётами. Старые записи не объявляются успешными задним числом. Новый API использует тот же административный контроль доступа, что остальные маршруты `/admin`.

## Серверная схема

`viewer_open_sessions`, миграция `w2b2c3d4e5f6` после актуальной на сервере `a2b3c4d5e6f7` (цепочка от `w1` содержит последующие бонусные миграции). Только новая таблица и индексы времени/пользователя. Никаких S3 PUT, изменений DICOM, compressor или прав пациентов. FK используют SET NULL при удалении исходной сущности.

Откат UI/API не требует удаления таблицы. Не выполнять downgrade с удалением собранной статистики при обычном откате приложения.

## Доставка через Git

По требованию пользователя на сервер код/статика поступают только через git push/pull. CRM — обычный коммит в её репозитории. Исходники viewer — в ветке разработки; готовая минифицированная сборка — отдельная `codex/viewer-static-production` с sourceCommit и SHA-256-манифестом. Публикация подготовленного билдa: `.scripts/publish-viewer-static.cjs`, затем push этой ветки. Секретный runtime app-config не включается в Git. Архивный CPU/Canvas-эксперимент исключён проверкой.

На сервере применяются миграция и graceful HUP Gunicorn для новых API. Перезапуск nginx/compressor не нужен. Статика активируется ссылкой на Git worktree проверенного release-коммита; прежние хешированные assets и runtime config доступны по локальным ссылкам для старых вкладок.

- В локальном браузере реальный сжатый образец: отчёт «Открыто», три MPR + панорама; время и аппаратный профиль появились в настоящем серверном API статистики (тестовая SQLite-БД).
- Отдельный сценарий блокировки WebGL 2 проверяет регистрацию ранней ошибки до монтирования просмотрщика.

Дальнейшие эксплуатационные ограничения: отчёт браузера не является защищённым от подделки аудитом действий врача; нет фонового сборщика полного console.log и гарантированной доставки после краха ОС. Накопленные отчёты нуждаются в согласованной политике хранения; автоматическое удаление исторических данных в этом изменении не включается.

## Исправление доставки HTTPS-отчётов 14.11.2026

После первой выкладки nginx зафиксировал два успешных GET `/api/viewer/telemetry/config` и два POST `/api/viewer/telemetry/sessions` с HTTP 400. Клиент отправлял POST с `referrerPolicy: 'no-referrer'`, а Flask-WTF при HTTPS и стандартном `WTF_CSRF_SSL_STRICT=True` требует Referer того же origin. Локальный HTTP-прогон не проверял это условие, поэтому не обнаружил проблему.

Для POST старта и обновления установлен `referrerPolicy: 'origin'`: передаётся только `https://admin.orbital3d.ru/`, без пути `/v/<token>`. CSRF-токен, проверка origin и авторизация сохранены. Bootstrap GET по-прежнему не передаёт Referer. Новый серверный HTTPS-тест подтверждает отклонение отсутствующего/чужого Referer и отсутствующего CSRF; безопасный origin позволяет сохранить старт и готовность. Клиентский тест проверяет обе отправки и отсутствие launchToken в обновлении.

Не доставленные ранее отчёты не восстанавливаются по used_at: это получение доступа, а не подтверждение отрисовки. Для проверки нужна новая вкладка исследования после обновления сборки.

Проверки исправления: клиентские тесты 6/6, серверные 8/8. На настоящем PostgreSQL повторён HTTPS-сценарий в rollback-only транзакции: отклонение запроса без Referer, приём старта с origin, готовность в агрегатах, поздняя ошибка/sequence и изоляция пользователя. Отсутствие тестовых строк после отката проверено. Production webpack — успешно, 3 прежних предупреждения. Изменён только клиентский транспорт; серверный runtime, схема БД и настройки CSRF не меняются.

# ORBITAL 3D iOS: этапы разработки и проверки сборок

Дата: 4 ноября 2026. Основание: [ТЗ приложения, редакция 2](doctor-ios-app-tz-2026-11-04.md).

Цель: двигаться короткими проверяемыми шагами. После каждого этапа пользователь собирает приложение, открывает на iPhone и даёт обратную связь. Сначала доказать настоящий офлайн-просмотр, затем расширять кабинет. Этот файл — план, ни один этап не помечен выполненным подготовкой документа.

## 1. Правила выполнения для агента

1. За один запрос выполнять **только названный пользователем этап**. После передачи результата остановиться для его компиляции/проверки. Следующий этап — по новой команде пользователя. Разрешение пройти один этап не означает разрешение сделать весь проект.
2. Каждый этап оставляет независимо собираемое приложение. Нельзя передавать изменения, которые «начнут собираться после следующих трёх этапов».
3. Уже проверенные функции сохраняются. В каждом следующем этапе коротко проверять предыдущий основной сценарий; интерфейс не перерисовывается заново без необходимости.
4. Для ранней проверки не ждать всех серверных API. Использовать изолированные Demo fixtures/тестовый источник; ясно показывать Demo. Медицинский рендер в этапах viewer — настоящий, а не картинка, видео или имитация жестов.
5. Production никогда не получает скрытый demo-login, доверие к dev-подписи/QR или автоматическую подстановку mock при сетевой ошибке.
6. Не дорабатывать CRM, production S3 или сервер viewer в клиентских этапах 1–14. Новые backend-функции — отдельная задача; этап 15 подключает уже реализованный согласованный API.
7. При риске архитектуры остановить зависимую работу и представить воспроизводимый результат/варианты. Не компенсировать неработающий локальный viewer переходом на сайт или старый просмотрщик.
8. Подготовленные исходники, успешная сборка в Xcode, запуск на симуляторе и проверка на физическом iPhone — разные статусы. В отчёте точно указать, что выполнено. В среде без macOS/Xcode нельзя заявлять, что iOS-сборка проверена.
9. После замечаний пользователя сначала исправить текущий этап, снова дать собираемый результат. Не прятать регрессии в очередь на конец проекта.

## 2. Единый формат контрольной сборки

На этапе 1 создать устойчивую структуру проекта и инструкцию сборки. Рекомендуемые имена: проект/target `OrbitalDoctor`, scheme `OrbitalDoctor-Demo` для проверок без CRM и позднее `OrbitalDoctor-Staging` для реального API. Это проектные имена, не утверждение о существующих файлах. Точное выбранное имя фиксируется в README и дальше не меняется без причины.

Для каждой поставки:

- Номер вида `E01.1`, `E02.1`; исправление после обратной связи увеличивает последнюю часть. Указать фактический CFBundleVersion/версию и источник сборки.
- Где открыть Xcode project/workspace, какой scheme/configuration и устройство выбрать, какие единожды настроить Team/Bundle Identifier. Не просить секреты подписи в репозитории.
- Если Xcode доступен — приложить результат сборки/тестов. Если нет — прямую отметку «Сборка Xcode не проверена в этой среде» и точные воспроизводимые действия для пользователя.
- Короткий список нового, маршрут по экранам на 5–10 минут, ожидаемый результат каждого действия, известные ограничения/неподключённые сервисы.
- Способ получить актуальные обезличенные тестовые данные/тестовый QR; без реальных ФИО, производственных токенов и чужих исследований в исходниках.
- Запись в журнале: исходники готовы / Xcode build / simulator / physical device / отзыв пользователя. Не считать этап принятым только по числу изменённых файлов или скриншоту.

Симулятор подходит для большинства экранов и ошибок. Камера QR, Face ID/Keychain, память/GPU, фоновые передачи и итоговый офлайн-тест требуют отдельной проверки на физическом устройстве. Сборки не должны зависеть от запущенного dev-сервера frontend на компьютере.

## 4. Подробное содержание этапов

### Этап 1. Первый запуск и визуальная оболочка

Сделать Xcode-проект, дизайн-токены, светлую тему, компактный фирменный логотип, нативную навигацию из пяти вкладок. Показать главную с вымышленными карточками и пример списка пациентов; в остальных разделах честно обозначить ещё не реализованные функции. Подготовить вход в «На устройстве». Шрифты/иконки/картинки не тянутся с CDN.

Проверка: собрать, пройти вкладки, открыть пример пациента, вернуться, увеличить системный шрифт, проверить маленький экран/клавиатуру. Пользователь оценивает внешний вид до развития функционала.

Готовность: проект запускается, нет обрезанных действий и горизонтальной прокрутки страницы. Demo доступ только в отдельной схеме; production-подключение пока не заявляется. Передать README сборки. Остановиться для отзыва о дизайне.

### Этап 2. Реальный локальный viewer: ранняя проверка архитектуры

Включить сборку нашего движка, WASM/JS-workers и все нужные ресурсы в приложение. Подключить локальный адаптер и синтетическую/проверенно обезличенную JPEG 2000 20× серию. На первом экране viewer достаточно большого аксиального вида и листания; проверить создание объёма, необходимое будущему MPR. Сеть для рендера не нужна. Записать capabilities локального WKWebView, память и время; проверять именно способ локальной поставки, не HTTPS-страницу на VPS.

Проверка: открыть тестовый снимок, пролистать, закрыть приложение полностью, включить авиарежим, запустить и открыть снова. При ещё не реализованной авторизации ранний fixture-сценарий находится только в Demo.

Готовность: реальные декодированные кадры и локальный volume; ни одного обязательного CDN/API/S3-запроса для открытия. Проверены WebGL/WASM/изоляция там, где нужны. Если выбранный способ не поддерживает движок, представить доказательство и скорректировать локальный адаптер до этапа 3; не продолжать декоративную оболочку поверх неработающего рендера.

### Этап 3. MPR и управление пальцами

Аксиальный/корональный/сагиттальный виды, один крупный viewport в portrait, переключение, синхронная координата креста, масштаб/перемещение, яркость/контраст, листание срезов и сброс. Landscape — крупный вид/два связанных окна. Координаты и настройки переживают поворот и переключение видов.

Проверка: выбрать заметную структуру, переключить все проекции, потянуть крест, изменить масштаб, повернуть телефон, вернуть fit. Всё в авиарежиме, без мыши и клавиатуры.

Готовность: точка/ориентации согласованы, пропорции сохранены, жесты не конфликтуют. Ранний тест из этапа 2 продолжает работать.

### Этап 4. Панорама и поперечные сечения

Добавить автопанораму, горизонтальную/вертикальную связь с MPR, мобильный редактор дуги, толщину/высоту, явное применение/отмену и поперечные сечения. Переиспользовать рассчитанный результат, не считать его заново при каждом движении креста. Все нужные вычисления/ресурсы локальные.

Проверка: открыть панораму, сопоставить крест с MPR, изменить дугу/слой, отменить и применить, открыть сечения. Повернуть телефон; изображение вписывается без деформации.

Готовность: панорама и сечения работают без сети, редактор удобен пальцами, кресты соответствуют выбранным координатам после редактирования. Нет лишнего чёрного хвоста в raster или растягивания по одной оси.

### Этап 5. Измерения и локальное сохранение работы

Длина/угол 2D и 3D, ломаная/плавная лента, выбор/перемещение/удаление, видимые «Готово»/«Отменить точку». Добавить LocalProjectStore: срезы, крест, настройки, дуга и измерения с UID/геометрией и версией схемы. Ошибка записи видна; «Сохранено на устройстве» означает фактическую запись.

Проверка: измерить, поправить точку, сохранить, полностью закрыть приложение, снова открыть офлайн и получить те же значения/позиции/дугу. Изменение zoom не меняет миллиметры. Проверить unsaved/error state.

Готовность: проект связан с конкретным локальным набором и не переносится на чужую геометрию. Синхронизации проекта с CRM пока нет и она не имитируется.

### Этап 6. Канал, импланты и 3D

Рисование/редактирование канала; локально доступная библиотека имплантов, выбор, установка, перемещение/поворот/параметры/удаление; 3D-череп с ленивой инициализацией. Дополнить проект предыдущего этапа каналом/имплантами. Мобильные панели не закрывают рабочую точку.

Проверка: провести канал, поставить/повернуть имплант, сменить MPR, открыть 3D, сохранить и перезапустить в авиарежиме. Убедиться, что модель и размеры восстановились; библиотека моделей не потребовала интернета.

Готовность: все обязательные инструменты доступны пальцами, сохранение совместимо с этапом 5, 3D освобождает ресурсы при закрытии. При необходимости этот этап разделяется на отдельно собираемые 6.1 «Канал» и 6.2 «Импланты/3D» до начала реализации.

### Этап 7. Библиотека «На устройстве» и скачивание

Создать постоянный локальный индекс, список/поиск/размер, очередь, отмену/повтор, staging, проверку состава/хешей, атомарную публикацию, восстановление после обрыва и удаление. Добавить нативный DownloadManager для изолированного тестового HTTPS-источника, не трогая CRM/S3 production. Тестовый источник может быть отдельным fixture-стендом; его настройка описана. Локальный импорт тестового набора — дополнительный dev-путь, не замена сетевому тесту download manager.

Проверка: скачать набор с видимым прогрессом, прервать/повторить, проверить неполный/повреждённый состав и недостаток диска. После ready выключить источник, закрыть приложение, включить авиарежим, открыть из «На устройстве». Удалить выбранное исследование и проверить освобождение места.

Готовность: прогресс транспорта реальный, ready только после проверки всех файлов, сохранённый набор не зависит от fixture-сервера. Проекты и уже готовые другие наборы не повреждаются. На этом этапе используются только тестовые данные; защита реального аккаунта завершается этапом 8.

### Этап 8. QR, устройство и локальная защита

Реальный сканер камеры, parser/валидация/доверенный сервер, состояния QR, подтверждение врача, Keychain, локальная блокировка и защищённое хранилище. Pairing transport пока mock, потому что backend ещё не разрабатываем. Сформировать воспроизводимый тестовый QR для экрана компьютера и явно пометить его dev-форматом/окружением.

Реализовать отдельный OfflineAccessVerifier на dev-подписях: привязка врача/устройства/сервера/наборов, expiry/clock anomaly, actions и изоляция ключей. Короткий access token, разрешение скачивания и офлайн-доступ имеют разные сроки. Структура подготовлена к будущему доверенному production ключу; нельзя принимать dev grant в production.

Проверка: камера разрешена/запрещена; QR правильный/чужой/истёкший; подключиться, скачать тестовый набор и открыть после перезапуска без сети. Истёкший mock access token при ещё действующем offlineGrant не закрывает локальное исследование. Проверить expiry offlineGrant, блокировку, выход и переподключение другим врачом.

Готовность: онлайн недоступен без нужной сессии, допустимый офлайн работает без API; чужое устройство/аккаунт не читает сохранённый набор. Подтверждённый тестовый revoke применяется; обычный timeout не выдаётся за revoke. В отчёте честно указать, что боевой QR ещё не реализован сервером.

### Этап 9. Пациенты, исследования и документы

Подключить mock repositories к реальным экранам: главная, списки/поиск/фильтры пациентов и исследований, создание/разрешённое редактирование, история, ready/pending/error/expired. Карточка ведёт в DownloadManager/локальный viewer. Добавить PDF/изображения, личные заметки, отдельные комментарии и меню share/download по capabilities; разделять основное и extra-исследование.

Проверка: найти пациента, открыть документ/снимок, скачать в библиотеку, вернуться к той же позиции списка. Изменить заметку, проверить «Предоставлен доступ», запрет чужого/нет права viewer, длинные ФИО и пустые состояния. Офлайн открыть только сохранённый набор, онлайн-операции не подтверждаются фиктивно.

Готовность: общий пользовательский путь работает с demo-данными, все действия привязаны к правильным ID/правам. Панель персонала, старый онлайн-viewer и Windows-функции не появились.

### Этап 10. Мобильная запись пациентов

Центр → день → крупные свободные слоты → пациент/услуга → подтверждение; отдельный agenda «Мои записи», перенос/отмена по правам, timezone и ограничения уже оформленного приёма. Справочники/availability — mock API с фиксированными сценариями, без отдельного самодельного desktop-календаря.

Проверка: записать demo-пациента, быстро нажать два раза, получить слот-конфликт, сменить центр/дату, потерять сеть и повторить. Проверить крупный шрифт, маленький экран и сохранение введённых полей.

Готовность: нет двух одинаковых записей, нельзя изменить чужую/заблокированную запись. Месяц выбирается отдельно, вся неделя не сжата в семь колонок.

### Этап 11. Направления и запросы

Пошаговое электронное направление, актуальная модель каталога/параметров, удобный выбор зубов, предпросмотр, список, отправка, удаление по правам, «Записать и отправить». Отдельно заказ бумажных направлений и история/формы восстановления старых снимков. Формы сохраняют черновик внутри защищённого сценария.

Проверка: создать стоматологическое и ЛОР-направление, выбрать/снять зубы, вернуться на предыдущий шаг, оформить вместе с записью. Отправить запрос бумажных бланков и восстановления, проверить результат/дубль/ошибку.

Готовность: мобильный сценарий покрывает реальные формы ТЗ, а не пустую кнопку «Скоро». Служебный флаг оплаты не доступен без capability. Отправка здесь подтверждается явно обозначенным mock backend, боевой результат не заявляется.

### Этап 12. Чат и поддержка

История с догрузкой, текст/время/статусы, реакции, unread/read, ответ сотрудников из mock transport, ошибка/повтор с client ID и обращение из контекста исследования. Поле ввода удобно над клавиатурой. Связать заказ бумажных направлений с чатом.

Проверка: написать длинное сообщение, свернуть/вернуть приложение, повторить после сбоя, проверить отсутствие дубля и корректный unread. Отправить обращение из исследования без автоматического вложения медицинских файлов/секретов.

Готовность: чужая переписка/старый аккаунт не появляются, закрытый чат не читает сообщения автоматически. Реальные push пока не требуются.

### Этап 13. Новости, уведомления, профиль и настройки

Новости/статья/комментарии/реакции, событие дня, центр уведомлений, профиль, email/push preferences, камера/локальная защита/подключение, управление хранилищем и поддержка. Подготовить маршруты входящего уведомления и адаптер APNs, без заявления, что production push уже работает.

Проверка: прочитать/ответить в новости, перейти из demo-уведомления к нужному исследованию, поменять настройки, открыть хранилище/профиль и выйти. Deep link проверяет аккаунт/ACL, неизвестный payload не открывает чужие данные. Проверить VoiceOver/увеличенный текст на готовых экранах.
